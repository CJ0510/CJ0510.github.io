Linux GPU/NPU加速器总体架构：CPU、GPU、NPU的本质区别

第1章：CPU、GPU、NPU到底有什么本质区别——执行模型、调度模型和内存模型

后面学习Linux GPU/NPU驱动时，我们会连续遇到context、job、queue、ring、firmware、GPUVM、IOMMU、partition、tile和fence。

如果直接把它们套进CPU调度器的task_struct → runqueue → CPU模型，很容易得到错误结论。例如：把一个GPU Job理解成一个Linux线程，把GPU Scheduler理解成CFS，或者认为CPU与集成GPU共享DDR就不再需要GPU虚拟内存。

1.2 不要先从“算力”理解CPU/GPU/NPU

1.3 CPU的核心设计目标

CPU希望尽快推进一条充满依赖、分支、异常和系统调用的指令流：

CPU愿意为此投入大量晶体管实现预测和乱序结构。它追求的不是同时放入最多算术单元，而是让一条通用指令流尽量少停顿。

1.5 Process、Thread、task_struct和Core

Linux使用task_struct统一表示可调度任务。用户口中的进程和线程都对应task；区别主要在于它们是否共享mm_struct、文件表、信号处理等资源。

CPU调度器的对象是task，而不是整个地址空间。一个多线程进程的不同线程可以同时运行在不同CPU Core上。

1.14 SIMT到底解决什么问题

SIMT（Single Instruction, Multiple Threads）让一组逻辑线程以相同指令流处理不同数据：

1.19 GPU Queue是什么

Queue至少要区分三个层级：

1.21 GPU Memory Model

CPU和GPU都需要地址翻译，但对象可能不同：

Linux主线DRM包含GEM/TTM、GPUVM、DRM Buddy、Sync Object等公共基础设施。它们分别解决Buffer对象、放置/迁移、GPU虚拟地址范围和同步等问题。

1.25 NPU为什么会出现

神经网络中大量工作由规律的矩阵乘、卷积、激活和张量变换构成。此类工作常受数据搬运和乘加能耗支配。针对访问模式、数值格式和数据流定制硬件，能够获得更好的Performance/Watt。

NPU不是一个严格统一的微架构名称，而是一类面向AI/张量工作负载的加速器。

1.26 NPU和GPU到底有什么不同

典型对比：

GPU也可以有Tensor Core，NPU也可以有VLIW/向量处理器，因此差异是“设计中心”而非绝对边界。源码分析时应以具体设备文档为准。

1.27 NPU的执行模型

NPU通常不暴露“每个神经元一个Linux线程”。KMD管理的是已编译程序、Buffer、Workload和设备资源绑定。

1.28 Graph、Workload、Program和Command

一个Workload可能携带输入输出Buffer、指令Buffer、Scratchpad需求、DMA描述符、Tile数量和依赖Fence。不同驱动命名会不同，必须回到UAPI和具体结构确认边界。

1.29 Tile、Compute Engine和Matrix Engine

NPU常把计算与本地存储组织成二维或分组Tile：

Tile可能包含向量/VLIW核心、本地Program/Data Memory、DMA端口和片上互连。Matrix Engine则更偏向执行MAC/矩阵指令。两者不是所有NPU都采用的统一术语。

1.30 Systolic Array的基本思想

Systolic Array让数据在处理单元之间有规律地流动并复用：

目标是减少反复访问外部DRAM，让权重、激活或部分和在阵列内部被多次使用。算术峰值只有在数据持续供给且布局匹配时才有意义。

1.31 Scratchpad为什么重要

Cache由硬件自动决定替换，Scratchpad/Local SRAM通常由编译器、Runtime或固件显式规划：

神经网络访问模式较可预测，显式管理能换取更确定的延迟、更高复用率和更低能耗；代价是编译器和Runtime必须正确完成Tiling与容量规划。

1.32 NPU为什么大量依赖DMA

在NPU上，数据搬运往往与计算同等重要：

性能瓶颈可能来自DDR带宽、DMA描述符、NoC拥塞、双缓冲失效或Scratchpad复用不足，而不是MAC单元数量。只看TOPS无法解释真实应用性能。

1.33 NPU的Spatial Scheduling

空间调度把不同物理区域同时分配给不同Workload：

调度器不仅决定“谁先运行”，还决定“占多少列、哪些Tile、本地存储与DMA资源”。资源分配与调度策略因此紧密耦合。

Linux主线AMD XDNA文档给出了现实例子：二维Compute/Memory Tile Array可在列边界形成隔离Partition，并绑定Workload Context。

1.34 NPU的Temporal Scheduling

时间调度让多个Workload轮流使用同一Partition：

AMD XDNA同时支持空间和时间共享。驱动中的Resource Solver决定阵列重新分区和Workload映射，固件执行Context到Column的绑定。这是具体实现示例，不应推广为所有NPU的强制架构。

1.35 CPU、GPU、NPU调度模型对比

CPU主要分配CPU时间；GPU KMD主要在Client间安排Job/Queue到Engine；NPU还可能同时分配空间资源。

1.38 Linux内核视角下三者如何统一

Linux不会把每个GPU Lane或NPU PE变成task，而是在系统边界管理更粗对象：

CPU task仍负责调用Runtime、提交命令、等待结果和处理异常；设备内部并行由加速器自己的执行机制负责。

1.39 DRM/accel为什么会成为公共基础设施

不同加速器共同面对：

Linux accel子系统明确复用DRM代码：accel设备是一类DRM设备，但使用独立设备节点/主设备号，避免图形用户栈误把纯计算加速器当作显示GPU。驱动代码放在drivers/accel/。

1.43 常见误区

误区1：GPU就是很多CPU Core

错误。GPU的执行粒度、控制流处理、调度层次和内存隐藏策略都不同。

误区2：GPU Thread等于Linux Thread

错误。GPU Lane没有task_struct，不由Linux CPU调度器逐个调度。

误区3：Linux GPU Scheduler调度Warp

通常错误。KMD更常调度Job、Entity或Queue；Warp/Wave由硬件层管理。

误区4：NPU就是没有图形功能的GPU

错误。典型NPU更强调Tensor/Dataflow、Scratchpad、DMA和空间资源。

误区5：GPU/NPU只有一个Scheduler

错误。Runtime、KMD、Firmware和Hardware都可能各有调度决策。

误区6：CPU和GPU共享DDR就不需要GPU内存管理

错误。仍需GPUVA、权限、页表/映射、缓存一致性、生命周期和同步。

误区7：Fence就是GPU版mutex

不准确。Fence表达异步活动的完成和依赖；mutex主要保护CPU临界区互斥。

误区8：NPU性能只看TOPS

错误。编译、Tiling、DMA、带宽、本地存储复用和资源分区都可能限制性能。
