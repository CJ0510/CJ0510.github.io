1.1 hung_task到底是什么

hung task是Linux发现“Task长时间处于特定阻塞状态并且没有可观察调度进展”的诊断机制。它打印Task、阻塞时长和栈，提醒系统可能存在长期I/O、锁等待、固件无响应或死锁。

1.6 TASK_UNINTERRUPTIBLE是什么

TASK_UNINTERRUPTIBLE表示Task等待一个不能被普通Signal随意打断的内核条件。用户态工具通常把它报告为D。

这是状态映射的实用近似；TASK_KILLABLE、TASK_IDLE等组合状态还带有额外语义，不能全部简单叫D。

二者都通常意味着Task已经睡眠并让出CPU。核心差别是允许哪些唤醒原因：

它们不是“轻度卡顿”和“重度卡顿”的等级关系。

1.8 为什么D状态不是“CPU卡死”

Task A在等待期间通常不消耗CPU。系统可能CPU idle很高，却因为大量关键Task都在D状态而几乎无法提供服务。

1.9 Task为什么要sleep

磁盘、网络、DMA、Firmware、锁和页面状态不会总是立即就绪。忙轮询会浪费CPU：

可睡眠上下文更适合登记等待者并让出CPU，条件成立后再唤醒。

1.10 为什么不能所有等待都用TASK_INTERRUPTIBLE

若一个底层事务已经把Buffer交给设备，Signal让调用者直接退出并不意味着DMA也停止。中断等待会引入取消、回滚、所有权和迟到完成等复杂状态。

只有API和底层状态机都能正确处理取消时，可中断等待才安全。

1.11 为什么Linux需要TASK_UNINTERRUPTIBLE

不可中断等待为必须完成的状态过渡提供简单约束：

它不是为了“禁止用户控制进程”，而是避免普通Signal把不能安全取消的内核事务撕开。

1.14 set_current_state()与__set_current_state()

v6.1的关键区别：

set_current_state()包含内存屏障，使状态写入与随后条件检查正确排序；__set_current_state()不提供这层序列化，适用于调用者已经通过同一把锁等方式保证顺序的场景。

若“登记睡眠状态→检查条件”与Producer的“更新条件→唤醒”排序错误，就可能发生条件已成立但Waiter错过唤醒的竞态。

schedule()不是造成卡住的根因，它只是实现睡眠的通用机制。

1.16 Wait Queue是什么

等待队列把“事件”和“等待该事件的Task”关联起来：

等待宏通常完成：加入队列、设置状态、反复检查条件、调度、被唤醒后清理队列项。直接手写这些步骤容易产生丢失唤醒。

1.17 Waiter、Wait Object、Owner、Producer四个角色

Completion未必有“Owner”，但一定有应该产生完成事件的Producer。

1.18 一个Task如何从D状态被唤醒

唤醒与实际运行是两个事件，中间可能存在runqueue等待。

1.19 wake_up()大体做什么

wake_up()遍历相应等待队列，调用等待项的唤醒函数。默认唤醒逻辑最终尝试把符合状态掩码的Task恢复为Runnable并入队。

它不会替Waiter修复条件；正确顺序通常是先发布条件变化，再执行唤醒。

1.20 Completion模型怎么理解

wait_for_completion()默认是不可中断等待。若IRQ丢失、错误路径漏掉complete()或Firmware不回包，Waiter就可能长期停在D状态。

1.21 mutex等待为什么也可能进入D状态

1.22 I/O等待为什么常见D状态

底层操作常不能靠普通Signal安全撤销，因此存储、NFS、Writeback和块设备异常经常表现为D状态。

1.25 正常D状态与异常D状态的区别

正常路径具有活跃Producer和有限完成时间；异常路径的条件长期不成立，或唤醒已经发生却因竞态未被Waiter观察。

应检查请求是否推进、Owner是否运行、IRQ计数是否变化、设备是否响应，而不是只统计D状态数量。

1.26 D状态什么时候会变成hung_task

D状态不会“转换成”一种叫hung task的新状态。检测线程周期性观察Task；当符合检测条件且超过配置阈值时打印警告。Task依然处于原来的等待状态。

1.28 为什么hung_task日志只是Symptom

日志打印被观察到的Waiter。比如栈停在wait_for_completion()，只证明它等待的Completion没有及时满足，不证明Completion实现有Bug。

1.29 为什么Waiter通常不是Root Cause

Waiter按设计睡眠，真正失去进展的往往是Owner/Producer：持锁者没释放、IRQ没来、Worker没执行、远端没回复或Firmware卡住。

调试必须从Waiter栈向外追，而不是在schedule()附近反复阅读。

1.30 本章最重要的Dependency模型

锁形成Owner链；Completion/I/O形成Producer链；复杂故障常是两者混合。

1.33 工程与性能意义

D状态Task不消耗大量CPU，但可能占有锁、Buffer、挂起请求或阻塞上层服务。大量D状态常对应I/O backlog、NFS stall、驱动/Firmware hang或Writeback停滞。

因此：

Linux负载统计会考虑某些不可中断任务，I/O卡顿可能造成高Load但低CPU利用率。

1.34 常见误区

误区1：D表示Dead

错误，通常表示不可中断睡眠。

误区2：D状态一直占CPU

错误，Task一般已经通过schedule()让出CPU。

误区3：D状态就是死锁

错误，正常短暂I/O也会出现D状态。

误区4：hung_task就是死锁检测器

错误，它报告长期无进展，不能直接证明依赖环。

误区5：栈顶等待函数就是根因

错误，它往往只是Wait Primitive。

误区6：wait_for_completion()卡住说明Completion有Bug

应先找谁负责complete()以及为什么没执行。

误区7：mutex_lock()卡住说明mutex实现有Bug

应追踪Owner及Owner的下一层依赖。

误区8：wake_up()后Task立即执行

错误，它先变为Runnable，何时执行由调度器决定。
