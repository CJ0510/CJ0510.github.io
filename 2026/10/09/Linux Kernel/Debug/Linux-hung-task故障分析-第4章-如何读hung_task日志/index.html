4.7 Tainted怎么看

taint是一组内核运行历史标志。不同字母占据固定位置，例如P常表示加载过专有模块，O表示加载过树外模块。它提醒你当前现场可能包含厂商或第三方代码，也会影响上游问题受理。

应按日志对应内核版本的tainted-kernels.rst解码，不要凭印象解释所有字符。

4.8 Call Trace是什么

Call Trace是该任务当前内核栈的符号化表示，展示函数调用关系和偏移。对hung_task而言，它主要告诉我们Waiter沿什么路径进入当前等待。

受架构、编译优化、内联、栈展开能力和符号质量影响，调用栈可能不完整或包含偏差。因此它是关键证据，但不是自动生成的根因报告。

4.17 如何识别IO Wait

io_schedule()、wait_on_page*()、块层请求等待和文件映射等待常提示I/O语义。它们表明任务的睡眠被标记为I/O等待，但不会自动告诉你是哪块磁盘或哪条request。

继续追踪具体page、bio、request、gendisk、队列、驱动和完成回调，并结合块层trace与设备日志验证。

4.18 如何识别Filesystem与NFS等待

本地文件系统栈可能出现filemap_*、页锁、writeback、journal和submit_bio；NFS路径常出现nfs_*、rpc_*、socket等待等。

4.20 怎么从源码找到Wait Object

固定步骤：

  1. 使用日志对应版本和配置找到Business Wait Point；
  2. 沿控制流定位等待API的直接调用点；
  3. 记录实参表达式及其所属结构体；
  4. 查对象在哪里初始化、如何关联当前请求、何时销毁；
  5. 若静态源码无法确定本次实例，使用vmcore、调试符号、trace或动态探针补充运行时地址。

不要拿其他版本中“名字相似”的实现替换现场版本。

目标是回答：依赖链下一节点当前在运行、Runnable，还是也在等待？

4.33 什么时候需要看NFS或RPC

出现nfs_*、rpc_*或网络等待时，应检查RPC任务状态、重传、挂载选项、网络连通性、收包路径和服务端状态。硬挂载在远端不可用时可能长期等待，这是策略和故障共同作用，不应直接归咎于本地调度器。

4.34 什么时候需要看Driver或Firmware

出现mailbox、DMA、设备命令或驱动私有wait helper时，按协议检查：命令是否真正发出，ring/FIFO是否推进，firmware是否接收，硬件状态机是否完成，IRQ/doorbell是否返回，错误恢复是否遗漏通知。

厂商模块taint可以提高调查优先级，但仍需完整证据链。

4.39 工程意义

结构化分析能避免“看到哪个函数就改哪个函数”。对驱动而言，把永久等待改成超时可以限制故障影响，但超时只是Fault Containment；硬件为何不完成、IRQ为何丢失仍是Root Cause问题。

高质量故障报告应该包含版本、配置、完整日志、对象与依赖链、验证证据及未确认假设，使问题可以复现和复核。

4.40 常见误区

误区1：Call Trace第一行就是Root Cause

栈顶通常是公共调度框架。

误区2：看到schedule()就怀疑调度器

绝大多数睡眠等待最终都会调用调度器。

误区3：wait_for_completion()卡住说明Completion坏了

应找具体Completion及Producer。

误区4：mutex_lock()卡住说明mutex实现坏了

应找具体锁、实际Owner和Owner的下一层依赖。

误区5：io_schedule()说明CPU调度异常

它主要表达I/O等待语义，应继续追request完成链。

误区6：静态源码能直接确定现场Owner

源码只能列出可能路径，实际Owner属于运行时状态。

误区7：多个相同栈一定等待同一对象

相同函数可以服务多个实例，必须验证对象地址和业务关联。

误区8：增加timeout就是根因修复

timeout可能避免永久挂起，但不解释事件为何没有完成。

误区9：Tainted证明第三方模块有Bug

它只说明环境历史，应作为调查上下文而非定罪证据。

4.41 博客总结

阅读hung_task日志应从事实提取开始：确认任务身份、PID、D状态、报告时长、内核版本和taint，再对Call Trace分层。__schedule()、schedule()等是公共睡眠框架；wait_for_completion()、mutex/rwsem慢路径、条件等待和io_schedule()揭示Wait Primitive；其下方第一个子系统函数通常是Business Wait Point。

Wait Primitive只回答“怎么等”，必须回到匹配版本源码，通过等待API实参确认Wait Object。mutex/rwsem继续寻找运行时Owner；Completion、wait_event和I/O继续寻找Producer及完成路径。多个hung任务先聚类并寻找Common Dependency，最终将结论分成Symptom、Immediate Cause和Root Cause，并为依赖图中的每条边附上证据或明确标为假设。
