2.1 为什么需要hung_task Detector

D状态本身是正常的：任务等待块设备I/O、Completion或内核锁时，都可能短暂进入不可中断睡眠。真正可疑的是：

这种故障不会必然让整台机器立即崩溃。其他CPU和任务可能仍在运行，因此需要一个独立观察者周期扫描系统，主动留下任务信息和调用栈。hung_task Detector就是这个观察者。

2.2 hung_task Detector运行在哪里

检测器运行在名为 khungtaskd 的内核线程中。它不是硬中断、软中断或定时器回调，而是一个可以睡眠、醒来并遍历任务的普通内核线程。

因此检测存在时间粒度，不会在任务刚进入D状态的瞬间报警。

2.14 Linux怎么判断Task有没有进展

检测器无法理解每个文件系统、驱动或网络协议的业务进度。它选择通用而廉价的代理指标：任务的上下文切换计数。

只要任务发生过新的上下文切换，这个总数就会改变，说明它在两次观察之间至少获得过某种调度活动。

这个指标具备三项优势：所有任务都有、读取便宜、与具体子系统无关。只要任务重新参与调度，计数通常就会变化。

2.20 第一次扫描为什么不会马上报警

第一次遇到一个已有切换记录的候选任务时，当前switch_count通常不同于缓存值，于是检测器更新基线后返回。下一轮扫描如果计数仍未变化，才继续检查last_switch_time + timeout * HZ是否已经到期。

还有一个保护：switch_count == 0的全新任务直接跳过，避免把从未正常切出过的新任务误判为hung。

2.22 hung_task_warnings

sysctl_hung_task_warnings是日志预算，v6.1默认初值为10。值大于0时，每打印一条hung task警告就递减；变成0后停止继续打印，避免永久故障造成日志风暴。

该sysctl允许最小值-1。由于代码只在大于0时递减，-1保持非零，可用于不限制警告次数。它限制的是警告输出，不等于关闭扫描。

2.27 hung_task Detector能检测什么

它擅长发现：

  • 长时间处于不可中断等待的任务；
  • I/O、锁、Completion或驱动路径上的长期无调度进展；
  • 系统尚能运行但局部任务链已经卡住的故障。

它提供的是“异常候选任务和现场入口”。

2.28 hung_task Detector不能检测什么

它不能直接回答：

  • 哪个mutex owner没有释放锁；
  • 哪个中断丢失；
  • 哪个设备寄存器或固件状态异常；
  • 哪个远端服务器没有响应；
  • 任务是否形成了严格意义上的环形死锁。

一直处于R状态的busy loop也不属于这条D状态检测主线；soft lockup、hard lockup、RCU stall分别有自己的检测机制。

2.29 False Positive与Long Latency问题

hung_task警告是启发式告警，不是deadlock proof。极慢存储、长时间NFS响应、设备调试暂停等场景，即使最终能恢复，也可能超过阈值。

阈值应该结合系统业务时延、最坏I/O延迟和故障恢复策略设置。阈值太短会制造噪声，太长又会降低故障发现速度。

2.32 工程与性能意义

周期扫描相比给每个D状态任务单独创建定时器更集中、简单，开销也更容易控制。与此同时，全系统任务遍历、打印大量栈和所有CPU回溯都不是免费的，因此存在check_count、检查间隔和warning budget等控制手段。

工程上应把hung事件当作抓取更多证据的触发点，例如冻结ftrace、保存块层和中断状态、采集锁依赖信息，而不是看到第一条栈就修改等待者代码。

2.33 常见误区

误区1：khungtaskd是定时器或中断

它是kthread_run()创建的内核线程，入口为watchdog()。

误区2：所有D状态都会立即报警

检测器会周期扫描，并要求切换计数长期不变且超过timeout。

误区3：timeout就是扫描间隔

timeout是无进展阈值，check interval是扫描频率，两者在watchdog()中共同决定行为。

误区4：check_interval=0关闭扫描

在v6.1中它表示使用timeout作为检查间隔；真正关闭检测的是timeout=0。

误区5：扫描所有含TASK_UNINTERRUPTIBLE的任务

源码还排除了TASK_WAKEKILL和TASK_NOLOAD，并在单任务检查中跳过冻结任务和零切换计数的新任务。

误区6：switch count变化代表业务完成

它只代表发生过调度活动，是“进展”的通用近似值。

误区7：日志秒数就是精确D状态持续时间

它基于last_switch_time和jiffies计算，还受扫描周期影响。

误区8：hung_task直接定位根因

它负责检测并打印现场，根因仍要沿Wait Object、Owner和Producer继续追踪。

2.34 博客总结

Linux v6.1的hung_task Detector由hung_task_init()创建khungtaskd内核线程，线程入口watchdog()按照timeout和check interval周期醒来。check_hung_uninterruptible_tasks()在RCU保护下遍历系统进程与线程，筛选包含TASK_UNINTERRUPTIBLE且不属于killable、idle类的候选任务；check_hung_task()再把nvcsw + nivcsw与任务保存的last_switch_count比较。如果计数发生变化，就更新last_switch_time，视为最近仍有调度进展；如果计数长期不变并超过timeout，内核便输出“blocked for more than … seconds”、任务信息和调用栈，并根据配置追加锁信息、所有CPU回溯或触发panic。

它能告诉我们“谁长时间没有动”，但不能自动回答“谁本来应该唤醒它，以及为什么没有唤醒”。
