6.1 为什么需要固定SOP

仅凭经验容易形成“看到栈、猜一个模块、改一点代码、问题暂时不再出现”的闭环，却没有证明因果关系。固定SOP要求把分析过程外显：

这样别人能够复核，你也能在下一次复现时继续补证，而不是重新猜测。

6.2 Step 1：确认现场是否可信

先记录现场质量：

  • 日志是否包含完整告警头和Call Trace；
  • 是否有多条hung任务、soft lockup、RCU stall或设备错误；
  • kernel release、构建号、配置、模块和taint；
  • 时间戳是否来自同一时钟域，日志是否丢失或乱序；
  • 系统是否仍存活，可否读取/proc与tracefs；
  • 是否有vmcore、pstore、串口日志或常驻trace。

现场不完整时应先标注能力边界，而不是用假设填空。

6.11 Step 10：识别First Non-progress Node

First Non-progress Node是沿依赖方向，第一个有证据显示应该推进却没有推进的节点。比如命令已提交，但之后没有设备完成状态和IRQ：停止点位于设备/IRQ完成链附近，而不是最外层mutex Waiter。

它不一定就是最终物理根因。IRQ缺失还可能由命令未真正启动、中断mask、firmware、时钟或硬件错误造成，需继续细化。

6.12 Step 11：补证据

为每条边建立证据卡：

四类证据各自回答不同问题：

类型 回答的问题 不能单独证明什么
Static Source 代码设计上谁应该做什么 现场是否真实执行
Runtime State 某一时刻对象和任务是什么状态 完整时间顺序
Temporal Trace 事件以什么顺序发生/缺失 未被trace覆盖的内部状态
Reproduction 故障是否稳定、修复是否相关 单独解释底层机制

结论严格分层：

Root Cause应解释“为什么不推进”，而不仅是重新描述“在哪里等待”。

6.14 Step 13：提出Fix方向

修复分三类，避免混写：

外部设备可能失效时，通常既需要根因修复，也需要containment防止永久D状态。

6.15 Step 14：设计Regression Test

回归测试至少覆盖：

  • 原始触发条件能否复现、修复后是否消失；
  • 并发和长时间压力；
  • 成功、失败、取消、超时、reset、remove等控制流；
  • 异常注入：丢IRQ、延迟Completion、I/O失败、firmware无响应；
  • 修复后是否存在泄漏、UAF、重复完成和迟到回调；
  • 关键延迟与吞吐是否退化。

测试应验证依赖链重新推进，而不只是“没有再次打印hung_task”。

6.18 如何处理现场已经消失

系统恢复后，当前/proc/<pid>/stack不再代表故障时刻。此时优先使用带时间戳的dmesg/串口、pstore、vmcore、保存的trace buffer、设备/firmware日志和业务请求ID。

若证据不足，只能输出已确认事实和下一次复现需要增加的观测点。不要用恢复后的现场替代历史现场。

6.30 本章实验

6.30.1 对历史日志跑完整SOP

禁止一步写Root Cause。依次填写Waiter、Primitive、Business Point、Object、Owner/Producer、Next Dependency，并为每一步标注证据强度。

6.30.2 每一跳写Claim与Evidence

6.30.3 构造两级依赖

在可恢复测试环境中让Task A等待由Task B持有的mutex，让B等待Completion，再由delayed work完成。观察正常链；随后跳过完成动作，比较A和B的栈与依赖图。模块必须具备安全退出和超时清理。

6.30.4 证据冲突练习

假设已观察到IRQ entry但Waiter仍未醒，列出至少五个替代假设，并为每个假设设计一个最小观测点。

6.30.5 写Bug Report

将一次分析整理为本章模板，邀请他人只根据报告复画依赖图。如果无法复画，说明对象、边或证据表达仍不够清楚。

6.31 工程意义

SOP把个人经验转换成团队可Review的工程资产。它帮助区分“代码设计上应该发生”和“故障现场实际发生”，减少误修和无效trace。

同一结构也适合自动化：解析栈、识别Wait Primitive、关联trace与请求ID、生成依赖图。但Wait Object实例解析和跨子系统语义仍需要版本匹配、调试符号和人工验证，不能把自动报告当最终结论。

6.32 常见误区

误区1：找到Wait Object就结束

还必须找Owner/Producer和下一层依赖。

误区2：找到Owner就结束

Owner可能也是Waiter。

误区3：源码有complete()就证明现场调用过

源码是Static Evidence，执行事实需要runtime/trace证据。

误区4：没有IRQ就是硬件损坏

命令、mask、routing、firmware、电源和时钟都可能造成相同现象。

误区5：稳定复现等于已经解释机制

复现提高可信度，但仍要证明停止节点和因果边。

误区6：timeout等于修复

timeout通常是containment，还要处理取消和迟到事件。

误区7：日志天然完整且按真实发生顺序输出

ring buffer覆盖、console延迟和多CPU交错都可能影响可见日志。

误区8：证据不足就不能写报告

可以明确写Confirmed、Strongly supported、Suspected或Unknown，并列出缺失证据。

误区9：trace越多越可靠

无目标的大量事件会增加开销、丢失和分析噪声，应围绕Claim采集。

6.33 博客总结

hung_task实战排查是一项依赖关系重建工作。先确认现场可信度和Waiter身份，从Call Trace识别Wait Primitive与Business Wait Point，再回到匹配版本源码确定具体Wait Object。锁对象寻找Owner，Completion、condition、I/O和设备事务寻找Producer；得到Owner/Producer后继续检查它的状态和下一层依赖，直到建立完整Dependency Graph并定位First Non-progress Node。

每条依赖边都应包含Claim、静态源码证据、运行时状态、时序trace、置信度和缺失证据。结论区分Symptom、Immediate Cause与Root Cause，修复区分Root Cause Fix、Fault Containment与Observability Improvement，回归测试则验证机制恢复、异常路径和迟到事件安全。证据不足时明确表达不确定性，比把合理推测包装成事实更专业。
