第8章：真实Case Study——从一条hung_task日志到Root Cause

0. Case边界、版本基线与证据声明

本章分析的真实日志头部是：

目前没有完整Call Trace、Wait Object地址、Owner/Producer栈、IRQ/I/O trace、设备寄存器和firmware日志。因此本章不会编造最终Root Cause，而是展示如何从有限事实建立可继续执行的Case Analysis。

前文的机制说明以主线Linux v6.1标签提交830b3c68c1fb1e9176028d02ef86f3cf76aa2476为基线；本案例运行的是厂商派生内核6.1.83-DR-PL5.1_V1.0.16。最终符号、调用路径和行为必须以该构建对应的源码、.config、vmlinux及模块为准，不能把主线v6.1路径直接当作现场事实。

8.3 第一步：只写事实，不做推断

可以确认：内核hung_task Detector报告as_mapreloc:3004长时间没有观察到调度进展，运行内核带有专有和树外模块taint标志。

不能确认：它在等锁、Completion、I/O还是远端服务；不能确认厂商模块就是责任方；更不能确认死锁、IRQ丢失或硬件损坏。

8.4 从state:D能确认什么

D是用户可见的不可中断睡眠表示，说明任务当前主要处于阻塞而非持续占CPU的busy loop。分析方向应转为：它怎样睡下、等待哪个对象、谁负责推进该对象。

仅凭D状态不能知道Wait Object，也不能区分正常长延迟和异常永久停滞。

8.5 从blocked >184s能确认什么

v6.1检测器根据任务context switch计数和last_switch_time判断长期无进展，日志秒数受扫描周期和调度时机影响。因此“超过184秒”是检测尺度，不是某个业务API入口的精密秒表。

它足以证明异常值得调查，但不足以证明准确起点。

8.6 从Tainted: P O能确认什么

按相应内核文档，P通常表示加载过专有模块，O表示树外模块。它说明现场不是纯上游内核，并提示需要厂商源码、符号和模块信息。

taint是环境证据，不是责任判定。必须用Wait Object和依赖链把问题连接到具体模块，才能评价其相关性。

完整栈决定第一层分类：

没有栈，就无法确认Wait Primitive，更无法解析Wait Object。

8.8 Case分析总路线

每一箭头必须附证据和置信度。

8.9 如果Call Trace显示wait_for_completion

只能先写：

回到厂商对应源码，定位类似wait_for_completion(&req->done)的直接调用点，记录req实例、生命周期和请求ID。随后搜索本对象的complete()、complete_all()及reinit_completion()路径。

8.10 Completion路径下一步怎么查

建立候选Producer列表：IRQ handler、threaded IRQ、worker、timer、DMA callback或另一个task。对每个Producer回答：是否被调度/触发、是否处理同一对象、是否走到complete分支、是否存在错误早退。

静态源码证明“应该完成”，trace或现场状态才能证明“实际执行过”。

8.14 如果Call Trace显示io_schedule

这说明睡眠具有I/O语义，但io_schedule()仍是框架。下一步从Business Wait Point定位page/folio、bio、request、journal、RPC或具体设备对象。

直接写“block layer bug”属于越过证据。

8.15 IO场景继续怎么查

本地存储链可能是：

用block issue/complete、queue状态、timeout/reset、IRQ和设备日志识别请求在哪一层停滞。需要request ID或设备/扇区等字段防止错误配对。

8.16 如果Call Trace显示NFS或RPC

依赖跨越本机和远端：

收集RPC状态与重传、挂载参数、网络收发、服务端和远端存储证据。客户端D状态可能只是远端故障的表现。

8.17 如果Call Trace显示Memory或Reclaim

try_to_free_pages()、dirty throttling、writeback或folio wait不能直接证明内存管理Bug。继续追：

记录GFP/order、zone水位、dirty/writeback、vmscan和块完成事件。

8.19 Case Analysis Template

8.20 怎样判断Confidence

本文采用四级：

当前案例Root Cause等级是Unknown。

8.21 Confirmed需要什么

至少应明确Wait Object、Owner/Producer和First Non-progress Node；依赖边有对象级现场或trace证据；替代假设得到检查；修复改变对应机制；旧版本复现而修复版本通过回归。

“改完后偶尔没再出现”不等于Confirmed。

8.22 Strongly Supported

例如源码证明Completion C只在IRQ X完成，trace确认命令提交后无IRQ X且buffer窗口完整，但缺少设备寄存器。可写：完成链在IRQ交付前停滞得到强支持，但无法区分mask、firmware或hardware。

8.23 Suspected

若只有一条wait_for_completion()栈和驱动函数名，只能怀疑Producer未推进。没有具体Completion、Producer和timeline时，不能升级为IRQ、firmware或硬件结论。

8.26 如果是Lock场景

需要证明M实例、B确实持有M、B的当前栈以及下一条依赖。若链最终回到as_mapreloc或已有节点，才调查Cycle。

8.27 如果是IO场景

每一层用对象ID、issue/complete、timeout、网络/设备状态证明。不能仅凭函数前缀合并不同请求。

8.28 真正要找的是First Non-progress Point

它是沿依赖方向第一个“应发生的进展没有发生”的边界。例如已确认submit和DMA start，而目标IRQ在完整窗口中缺失，则停止区间位于DMA完成、硬件/firmware和IRQ交付之间。

这仍是区间而非最终根因，需要更多底层状态继续缩小。

在尚不知分类时，从低开销基础事件开始：

8.33 异常时间线

“没有事件”只有在event已启用、filter正确、window完整且无drop时才有证明力。

8.34 为什么不要只靠dmesg

dmesg善于保存告警和离散状态，但console输出延迟、多CPU交错、ring覆盖及printk扰动使其难以还原细粒度时序。它通常告诉你最终症状，不一定保存最后一次submit、IRQ和wake。

8.35 为什么不要只靠ftrace

trace说明事件发生顺序，源码解释这些事件的契约和对象关系，运行时状态补充未被trace覆盖的内部值，复现验证因果稳定性。

四者相互印证才构成强证据。

8.36 真实Case分析阶段1：Static Analysis

拿到完整栈和对应厂商源码后：标记框架帧、Wait Primitive、Business Point；定位调用实参；记录Wait Object生命周期；搜索Owner/Producer、完成、唤醒、取消和错误路径；画Expected Dependency Chain。

主线v6.1只用于理解机制，不能替代厂商补丁源码。

8.37 真实Case分析阶段2：Runtime Analysis

现场仍在时采集：

记录采集时间，避免把不同时间点状态错误拼成同时态。

8.38 真实Case分析阶段3：Temporal Analysis

Flight Recorder回答：Waiter何时切出、是否被wake、Producer是否运行、IRQ是否到达、request是否issue/complete、driver状态机最后停在哪个事件。

输出是带ID的Actual Timeline，而不是一堆未经关联的trace文本。

8.39 真实Case分析阶段4：Reproduction

记录触发条件、频率、负载、硬件和环境。多次复现是否停在同一对象和First Non-progress区间，决定假设可信度。

复现不解释机制，但能检验证据是否稳定以及修复是否真正相关。

8.40 真实Case分析阶段5：Fault Injection

在测试环境模拟怀疑的异常：延迟或跳过Completion、屏蔽测试IRQ、让firmware不回复、注入I/O错误或持锁延迟。比较生成的stack、timeline和恢复行为是否与现场同构。

异常注入必须具备超时、reset和安全退出，不能在生产机制造不可恢复D状态。

8.41 如何避免错误修复

把wait_for_completion()改成timeout后告警消失，只证明永久等待被限制，不证明Producer故障修复。还要检查迟到Completion、对象回收、重复完成、reset并发和错误返回传播。

修复验收应针对First Non-progress机制，而不是仅针对告警文本。

8.42 应该同时记录三类Fix

三者可以同时需要，但报告中不能互相替代。

8.43 Root Cause Fix例子

根据最终证据可能是：补正确的IRQ使能/路由、修正DMA descriptor或IOMMU映射、补齐错误路径complete()、统一锁顺序、修复firmware状态机。

在当前案例尚未获得完整栈前，以上都只是类别示例，不是修复建议。

8.44 Fault Containment例子

带超时等待、命令取消、设备reset、有限重试、fail-fast和功能降级可以防止单个外部故障无限传播。必须定义超时后的对象所有权和迟到回调处理。

8.45 Observability Improvement例子

增加command ID、最后提交/完成ID、IRQ计数、timeout状态快照、driver tracepoint、pstore或可导出的Flight Recorder。观测改进应有开销预算和敏感信息审查。

8.46 Regression Test怎么设计

至少包含原场景、长稳、高并发、资源压力、错误注入、reset/recovery、设备remove以及性能回归。每个测试验证：任务不会永久D、错误正确返回、对象生命周期安全、依赖链能恢复推进。

8.47 对于Driver类问题

覆盖正常完成、IRQ延迟/缺失、DMA timeout、firmware不回复、设备reset、迟到IRQ和并发命令。检查重复完成、UAF、资源泄漏和错误码。

8.48 对于Lock类问题

覆盖高竞争、不同锁顺序、异常早退、取消、嵌套锁和Owner下游阻塞。启用合适调试配置时结合lockdep，但不能只以“无lockdep告警”判定通过。

8.49 对于NFS或IO类问题

覆盖网络延迟/断链、服务端不可用、存储慢/timeout、队列freeze、重连和恢复。验证挂载/重试策略符合业务期望，并能保留诊断证据。

8.54 如果只有一次现场怎么办

立即保存完整dmesg/串口、内核构建信息、模块列表、taint、all task stacks、/proc/interrupts、目标PID stack/status、trace buffer、设备寄存器和firmware日志。原始文件只读归档，分析时制作副本。

采集动作本身可能改变现场，应按价值和风险排序。

8.55 如果系统很快恢复

恢复后的/proc只表示当前状态，不能代替故障时状态。下一版应部署常驻Flight Recorder，在driver timeout或更早错误点snapshot/traceoff，并持久化关键状态。

8.56 如果系统完全卡死

可评估hung_task_panic配合kdump、ramoops/pstore、硬件watchdog dump或平台崩溃采集。启用panic会把局部阻塞升级为系统重启，必须评估服务可用性、dump可靠性和存储容量。

8.57 为什么Case Study最终必须可复现

完整闭环是：旧版本在受控条件复现、证据稳定指向同一停止点、修复直接改变机制、新版本通过原场景和异常注入、性能与恢复能力无回归。

无法稳定复现时仍可修复高置信度问题，但报告必须保留不确定性与后续观测计划。

8.59 本章最重要的设计思想

  1. 真实案例先分Fact和Hypothesis。
  2. D状态与184秒只证明长期不可中断等待，不证明具体子系统责任。
  3. 厂商6.1.83派生内核必须使用匹配源码、配置和符号。
  4. 完整Call Trace是确定Wait Primitive的第一关键证据。
  5. Wait Primitive之后继续找对象、Owner/Producer和下一跳。
  6. First Non-progress Point比最外层Waiter更接近根因。
  7. 缺失事件只有在采集完整性得到证明后才有意义。
  8. Source、Runtime、Trace和Reproduction应相互验证。
  9. 修复分为Root Cause、Containment和Observability三类。
  10. 没有证据闭环时，明确写Unknown比虚构Root Cause更有价值。

8.60 博客总结

as_mapreloc:3004 blocked for more than 184 seconds目前只能证明该任务被hung_task Detector判定为长期无调度进展的不可中断等待者，并且运行在带专有和树外模块taint的厂商6.1.83派生内核上。缺少完整Call Trace意味着连Wait Primitive都尚未确认，因此Root Cause必须保持Unknown。

正确的下一步是取得匹配的vendor源码、.config、vmlinux和模块符号，完整符号化栈；从Business Wait Point的实参确定Wait Object；对锁找Owner，对Completion、condition和I/O找Producer；递归构建Dependency Graph，再用运行时状态和Flight Recorder Timeline确定First Non-progress Point。最终通过Claim-Evidence-Confidence表区分直接事实、强支持推断和未知项。

这正是成熟调试和“看见D状态就猜Driver/IO/死锁”的区别：结论的强度永远不能超过证据。
