Linux hung_task故障分析：用ftrace与trace-cmd构建Flight Recorder

第7章：hung_task Flight Recorder——用ftrace与trace-cmd自动保留异常现场

0. 源码基线、工具边界与安全说明

本文以内核 Linux v6.1 为基线，对应上游标签提交830b3c68c1fb1e9176028d02ef86f3cf76aa2476。主要参考：

7.1 为什么需要Flight Recorder

hung_task检测关注长期无进展，告警可能在初始故障发生几十秒甚至几分钟后出现。真正关键的命令提交、DMA启动、中断丢失或错误状态迁移早已过去。

Flight Recorder平时只在固定内存中循环保存最近历史，异常发生时冻结或复制缓冲区，弥合“故障发生”和“检测到故障”之间的Observability Gap。

7.2 为什么事后开始trace太晚

在最后一步才启动trace，只能看见告警之后。正确策略是故障前已开始记录，并尽可能在driver timeout或首个异常状态处冻结，而不是等hung_task阈值到期。

7.3 ftrace Ring Buffer是什么

ftrace把事件写入内核ring buffer。buffer容量固定，新记录持续推进写位置；在overwrite模式下，空间不足会覆盖最老数据。因此它保存的是“最近一段历史”，而不是无限日志。

trace输出是buffer内容的视图，读取、清空、关闭写入是不同操作，不能混为一谈。

7.4 Ring Buffer为什么适合异常诊断

相比长期把所有事件写入文件，内存ring buffer具有固定容量、无需持续存储I/O、可在异常点冻结的特点。代价是历史长度有限，异常冻结过晚会覆盖根因事件。

Flight Recorder设计目标不是“保存一切”，而是用有限开销保存足以回答当前依赖链问题的历史。

7.5 per-CPU Ring Buffer

ftrace通常为各CPU维护buffer，降低多CPU写入同一全局结构造成的竞争。事件天然携带CPU上下文，离线时再按时间戳合并。

这也意味着高事件率CPU可能比其他CPU更快覆盖历史，不能只用系统总buffer除以总事件率粗略判断每个CPU窗口。

7.10 tracing_on是什么

每个tracing instance有tracing_on控制是否允许继续记录：

它不是event选择器。事件可以仍处于enable状态，而instance暂时不向buffer写入。

7.11 tracing_on=0发生什么

写0会冻结现有buffer内容，通常不会清空历史；因此之后仍可读取trace或使用工具导出。

“停止记录”不等于绝对零开销：已启用的tracepoint静态分支、触发器和工具状态仍可能有不同程度成本。若长期停用，应按目标设计决定是否同时disable events。

7.14 snapshot是什么

snapshot为当前instance维护一份快照buffer。触发snapshot时保存当前历史，主buffer随后可继续接收新事件，从而同时保留“触发前历史”和“触发后过程”。

snapshot需要相应内核配置、内存和接口支持；应先确认/sys/kernel/tracing/snapshot存在。它不是把数据自动写到磁盘。

7.15 snapshot和traceoff区别

traceoff更简单、内存更少且不怕触发后覆盖；snapshot适合还需观察恢复、reset或后续阶段，但必须单独导出snapshot和当前buffer。

7.16 hung_task应该选traceoff还是snapshot

只关注首次异常、系统可立即采集时，优先traceoff。既要保留异常前历史，又要观察自动恢复过程时选择snapshot。

真正关键是触发时机：driver在5秒命令超时处冻结，通常比120秒后的hung_task告警更能保留根因窗口。

7.20 irq_handler_entry与irq_handler_exit

这两个事件回答预期硬中断是否进入、退出以及大致处理时长。它们不能自动证明ISR执行到哪个分支，也不能证明设备完成状态正确。

因此硬件Completion问题通常还要增加驱动状态或自定义tracepoint。

7.21 softirq

网络接收、tasklet或其他延后处理依赖softirq时，可按需启用softirq_raise、softirq_entry和softirq_exit。这样可以区分硬中断已到但后续softirq未运行，还是整个中断链未发生。

7.22 block_rq_issue与block_rq_complete

块事件可验证request是否发出以及是否完成，并计算可观察的I/O延迟。事件名称和字段会受内核配置与版本影响，先查看：

issue没有complete是重要证据，但还要考虑采集窗口、request重排、merge和ID关联。

7.23 Workqueue

常用事件包括workqueue_queue_work、workqueue_execute_start和workqueue_execute_end。它们区分：work未入队、已入队未执行、正在执行未结束。

要确认work地址、函数和目标queue，避免把不同实例的相同work函数混在一起。

7.24 Timer

超时、重试和恢复由timer驱动时，可按需启用timer事件，验证timer是否启动、到期和执行。timer到期不等于回调内恢复动作成功，因此关键分支仍建议加入自定义事件。

7.25 NFS与RPC

只有分类已指向网络文件系统时才加入nfs/rpc事件，并先查看目标机available_events。需要关联RPC task、xid、server和重传，单纯增加所有网络事件会迅速耗尽buffer。

7.29 怎么关联PID或TID

ftrace事件本身带有当前上下文信息，但IRQ发生时current未必是原始提交者。Driver事件应在请求对象中保存并输出submitter PID/TID或业务ID，不能用ISR执行时的current代替提交任务。

7.30 怎么关联CPU

CPU字段用于连接sched、IRQ和driver事件，并发现迁移。由于buffer是per-CPU，跨CPU合并依赖trace clock；相同时间戳附近应结合因果ID，而不是只靠显示顺序判断先后。

7.31 怎么关联IRQ

记录Linux IRQ number、设备/queue/vector以及ISR内读取的状态位。共享IRQ场景下，“handler entry”只证明该IRQ线被处理，不证明目标设备声称中断，必须结合状态位或driver trace。

7.32 怎么从hung_task触发traceoff

可选层次：

v6.1默认hung_task告警不会替你冻结任意自建instance。触发方案必须显式设计和测试。

7.33 内核触发方式

在driver或内核明确异常点调用tracing_off()响应快，但它可能影响全局top instance，而且与自建instance关系需按实现核实。产品化方案更适合使用专用trace event，再由instance event trigger执行动作。

修改kernel/hung_task.c直接冻结trace属于定制内核行为，也可能在120秒后才触发，未必保存最早事件。

7.34 Userspace触发方式

守护进程可监控kmsg、uevent或设备健康接口，检测异常后写目标instance的tracing_on=0，再导出。优点是无需内核改动；缺点是调度、日志传递和脚本处理存在延迟，旧事件可能继续被覆盖。

脚本还需处理多次触发、权限、存储空间和服务重启。

7.35 Event Trigger方式

已有错误/超时trace event时，可向其trigger文件配置traceoff或snapshot，并用event filter限定设备、request或错误码。优势是触发发生在内核事件点附近。

应先用测试event验证trigger是否作用于预期instance、能否一次触发、如何清除配置以及快照是否可读。

7.36 trace-cmd start

trace-cmd start配置并启动内核tracing，但不持续把事件流写成最终trace.dat，适合Flight Recorder。概念命令：

buffer大小、clock、过滤和instance参数应根据所装trace-cmd版本显式配置并核对。

7.37 trace-cmd stop

trace-cmd stop停止tracing但不以清空buffer为目的，因此可以在后续执行extract。它与内核trigger冻结的区别在于控制路径和延迟：命令发出前事件仍可能继续写入。

不要在extract前执行trace-cmd reset或向trace文件写空操作，否则可能破坏现场。

7.38 trace-cmd extract

trace-cmd extract从现有内核buffer生成trace.dat，通常用于start -> 异常 -> stop/traceoff -> extract流程。导出后可用：

或KernelShark查看。snapshot和自定义instance的导出选项取决于trace-cmd版本，应提前演练，不能等线上故障后才研究命令。

7.39 record和start/extract区别

trace-cmd record负责启动、收集并在结束时写出文件，适合有明确开始/结束的实验；Flight Recorder更希望事件常驻内核固定buffer，只在异常后落盘，因此通常使用start和extract组合。

二者并非谁绝对更好，选择依据是采集窗口、持续时间、存储写入和触发方式。

7.40 怎么检查Ring Buffer overrun

查看目标instance的：

关注entries、overrun、dropped events、bytes、oldest event ts等目标内核实际提供字段。overwrite模式中overrun增长表示旧记录被覆盖，是设计行为；真正指标是最老事件是否仍早于所需故障前兆。

7.41 怎么控制Tracing开销

按优先级优化：

  1. 只启用能验证Dependency Chain的tracepoint；
  2. 使用event filter缩小设备、PID或状态；
  3. 减少事件字段和高频事件；
  4. 调整每CPU buffer，不盲目扩大；
  5. 在真实负载下测量CPU、延迟、内存与窗口；
  6. 记录丢失和覆盖统计。

必须同时比较Tracing关闭与开启的业务基线。

7.42 为什么不要全开function tracer

全系统function/function_graph事件率极高，会增加执行开销并让短buffer只剩极短历史。hung_task通常需要几十秒甚至更长窗口，因此应坚持event-first。

必须使用function tracer时，用set_ftrace_filter等机制限制到少量关键函数，并实测开销和覆盖窗口。

7.43 Trace Clock怎么选

trace_clock列出可用时钟，方括号表示当前选择。local时钟开销低，但跨CPU排序特性可能不如global类时钟直观；global通常更适合跨CPU因果分析，但可能有额外开销。

选择前先查看目标机说明，切换后在多CPU测试中验证单调性和成本。一次证据集必须记录使用的clock。

7.44 Trace Instance是什么

tracefs的instances/允许创建独立tracing instance，每个instance拥有自己的buffer、events、filters和tracing_on。实例隔离能防止其他调试会话修改主Flight Recorder配置。

并非所有tracer和功能都可在所有instance完全独立使用，需按v6.1文档和目标配置验证。

7.53 本章实验

7.53.1 基础Flight Recorder

在测试机只启用sched与IRQ事件，运行负载后手工写tracing_on=0，确认旧数据保留并能导出。

7.53.2 测量History Window

分别在空闲和真实压力下运行30、60、120秒，读取per-CPU stats和最老/最新时间戳，记录各CPU实际窗口。

7.53.3 对比事件集合

依次测试sched、sched+irq、sched+irq+block，测量事件率、overrun、CPU/延迟开销，选择满足目标窗口的最小集合。

7.53.4 验证snapshot

确认接口和配置存在后，在触发点执行snapshot，验证snapshot历史固定而主buffer继续变化，并提前练习两个buffer的导出方法。

7.53.5 Completion Hang

在具备安全清理的测试模块中故意不complete()，用driver事件记录submit和timeout，捕获最后一次sched switch及缺失wake。不要在生产系统制造永久D状态。

7.53.6 自动触发

为测试timeout event配置过滤与traceoff trigger，验证只冻结目标设备/请求，重复触发不会破坏第一份现场。

7.53.7 离线还原

用trace-cmd report或KernelShark建立Scheduler、IRQ和Driver三个时间轴，标出最后已确认事件、首个缺失预期事件及证据限制。

7.54 工程意义

Flight Recorder把偶发、不可即时复现的hung_task从“只有最终栈”提升为“具有故障前历史”。Dependency Graph说明谁依赖谁，Timeline说明依赖从何时停止推进，两者结合才能建立强因果证据。

它也要求产品化设计：内存预算、低开销事件、稳定ID、一次性触发、持久化、隐私和自动清理都必须纳入方案。

7.55 常见误区

误区1：hung_task出现后再开始trace

关键前史通常已丢失。

误区2：tracing_on=0会清空buffer

它用于停止继续写入，已有记录通常保留。

误区3：停止tracing等于绝对零开销

已配置event、trigger和工具状态仍可能有成本，需实测。

误区4：buffer越大越好

还要考虑每CPU内存、snapshot、instance和目标窗口。

误区5：event越多越好

高事件率会增加开销并更快覆盖真正需要的历史。

误区6：function_graph适合长期全开

通常数据量过大；Flight Recorder应优先语义tracepoint。

误区7：snapshot和traceoff相同

前者保存触发历史并继续记录，后者冻结当前buffer。

误区8：trace-cmd stop后不能extract

stop的Flight Recorder用途正是停止写入后再extract；不要先reset。

误区9：overrun代表采集失败

overwrite模式允许覆盖；判断标准是所需History Window是否仍在。

误区10：IRQ entry证明目标设备完成

共享IRQ和错误状态都可能产生entry，需检查driver状态位和Completion事件。

误区11：缺失事件必然表示事件没有发生

还要排除event未启用、filter错误、窗口覆盖和记录丢失。

7.56 博客总结

hung_task的检测延迟决定了事后启动trace通常过晚。有效方案是在故障前使用低开销tracepoint持续写入per-CPU ring buffer，并在接近First Non-progress Point的driver timeout或错误event处执行traceoff或snapshot。traceoff冻结唯一现场；snapshot保留触发前历史并允许继续观察恢复过程。

事件集合应围绕Dependency Chain选择：sched重建Waiter睡眠与唤醒，IRQ确认硬件中断，workqueue确认Producer是否执行，block确认请求issue/complete，自定义driver tracepoint以request ID连接submit、DMA、IRQ、complete、timeout和reset。buffer大小最终要用真实负载下的History Window验证，而不是凭容量猜测。

离线分析通过统一clock和对象ID合并Scheduler、IRQ、I/O与Driver Timeline。Dependency Graph回答“谁依赖谁”，Temporal Timeline回答“从什么时候开始不推进”，二者共同把单条Call Trace升级为可验证的Root Cause证据。
