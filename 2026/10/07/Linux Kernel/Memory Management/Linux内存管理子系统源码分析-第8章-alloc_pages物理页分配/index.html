Linux内存管理子系统源码分析：alloc_pages物理页分配

第8章：alloc_pages()——一个物理页到底是怎么从Linux中分配出来的？

上一章建立了Buddy System的静态模型：zone->free_area[]按order和迁移类型保存空闲物理块，大块可以拆分，小块释放后可以合并。

这一章把模型放进真实调用链。我们的目标不是只记住“alloc_pages()会从Buddy取页”，而是回答：内核怎样确定可用Zone、怎样保护水位、为什么先查PCP、什么时候进入Buddy，以及快速路径失败后为什么还要进入慢速路径。

8.27 order-0为什么优先走PCP

order-0是系统最常见的页请求，例如匿名页、页缓存和许多内核对象的底层页。给它建立CPU本地缓存能显著减少全局Zone锁竞争。

但这里要纠正一个常见简化：

Linux v6.1的PCP不只缓存order-0。pcp_allowed_order()默认还允许不超过PAGE_ALLOC_COSTLY_ORDER的低阶请求，通常是order 0~3；某些THP配置还可能允许特定order。

所以准确说法是：order-0最典型、最高频；符合pcp_allowed_order()的低成本高阶页也可能走PCP。

8.28 PCP模型

PCP并不创造额外物理页。页面从Buddy批量移入PCP后，仍属于该Zone的空闲资源，只是放在CPU局部链表中以加速分配与释放。

8.57 常见误区

误区1：alloc_pages()返回虚拟地址

错误。它返回struct page *。是否能通过page_address()获得永久虚拟地址取决于架构和页面类型。

误区2：有足够free内存，高阶分配就一定成功

错误。高阶分配需要物理连续块，总量足够不等于连续性足够。

误区3：GFP_ATOMIC一定成功

错误。它不能睡眠和直接回收，虽然优先级更高、可用部分储备，仍然可能返回NULL。

误区4：PCP只缓存order-0

对旧式教学模型有帮助，但不符合v6.1完整实现。v6.1默认允许低成本order 0~3进入PCP，具体由pcp_allowed_order()决定。

误区5：rmqueue()只操作Buddy

错误。它是统一取页入口，先判断PCP路径，未命中或不允许时才进入rmqueue_buddy()。

误区6：fast path失败就是OOM

错误。它只表示当前条件下不能直接取页，之后可能通过回收、规整、调整权限或重试成功。

8.58 本章最重要的设计思想

8.58.1 先缩小搜索空间，再取页

策略先决定“可以去哪”，底层才决定“怎样拿”。

8.58.2 空闲页也分可不可用

Watermark、lowmem reserve、cpuset、CMA和迁移类型共同决定当前请求能否使用某页。

8.58.3 高频路径局部化

PCP把最常见分配从共享Zone锁前移到CPU局部缓存。

8.58.4 快慢路径分离

绝大多数请求保持快速；只有资源紧张时才支付回收、规整和重试成本。

8.58.5 现在成功不能破坏未来恢复能力

水位和储备不是浪费内存，而是在压力下为系统保留自救空间。
