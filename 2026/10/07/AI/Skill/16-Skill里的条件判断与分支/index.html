现实任务很少沿着一条固定直线执行。例如性能分析可能遇到：

但真正可靠的分支远比几句 if 复杂。我们还必须回答：

  • 条件来自用户输入还是工具证据？
  • 多个条件同时成立时，执行一个还是多个分支？
  • 条件不明确时能否推断？

本章的核心认知是：

Skill 中的分支不是写作上的“视情况而定”，而是由可观察状态驱动、具有明确优先级和出口条件的控制流。

1. 这一章要解决什么问题

本章集中回答：

目标是让 Agent 在不同输入、证据和执行状态下选择正确路径，而不是依赖临场发挥。

2. 为什么 Skill 不能只有线性步骤

线性 Workflow 假设所有任务都具有相同输入、证据和成功路径：

真实任务却可能出现：

  • 输入格式不同；
  • 用户目标不同；
  • 可用工具不同；
  • 证据指向不同领域；
  • 有些步骤需要授权；
  • 有些结果不完整；
  • 有些任务只需分析，有些还要执行修改；
  • 某些场景必须停止。

如果没有显式分支，Agent 可能：

  • 对所有输入执行全部步骤；
  • 调用无关工具；
  • 在证据不足时继续推断；
  • 把只读请求升级成写操作；
  • 缺少参数时自行猜测；
  • 跳过某些边界场景。

OpenAI 官方 Cookbook 将“高度条件化、像复杂流程图一样分支”的工作流列为适合封装成 Skill 的典型场景。Skill 的价值不仅在于复用步骤，还在于复用决策逻辑。

3. 整体架构：条件来自状态，分支改变状态

这里有两个关键要求：

  1. 条件必须基于已经观察或验证的状态；
  2. 分支执行后必须更新状态并验证结果。

因此，分支不是孤立的 if，而是状态机中的转移。

5. 条件必须可观察、可判定

差的条件：

问题在于：

  • “可疑”没有定义；
  • 没有证据来源；
  • 不知道调查什么；
  • 无法编写测试。

更好的条件：

一个可判定条件通常需要：

  • 字段或信号；
  • 比较方式；
  • 阈值或枚举；
  • 时间范围；
  • 单位；
  • 数据完整性要求；
  • unknown 的处理方式。

6. 条件的六种常见来源

6.1 用户意图

6.2 输入特征

6.3 工具或脚本结果

6.4 环境能力

6.5 权限与授权

6.6 工作流状态

不要把这些来源混成一句模糊的“如果合适”。

8. if / else if：互斥分支

当同一任务只能选择一条路径时，使用互斥分支。

8.1 必须定义判定顺序

如果一个输入可能同时匹配多个条件，先后顺序会改变结果。

8.2 条件应互斥或显式说明优先级

例如通过规范化步骤先得到唯一的 input_format，比多次模糊匹配扩展名更可靠。

8.3 必须有 else

没有默认出口时，未知格式可能意外落入某个分支。

9. 多个独立 if：可组合分支

性能问题可能同时涉及调度、内存和 I/O，不能用 else if 强迫只选一个。

9.1 可组合分支的特点

  • 多条路径可以同时执行；
  • 每条路径拥有独立证据；
  • 结果最后需要汇合；
  • 一个分支失败不一定阻止其他分支；
  • 汇合阶段要处理冲突和不完整结果。

9.2 汇合点不可缺失

如果只有分叉没有汇合，最终报告可能只是几段互不关联的结果。

10. 优先级：多个条件同时成立怎么办

常见优先级规则：

10.1 安全优先

10.2 输入有效性优先

输入未验证时，不能进入分析分支。

10.3 用户明确意图优先

用户明确要求只读分析时，即使写工具可用，也不能进入修改分支。

10.4 更具体条件优先

10.5 阻断性条件优先

权限缺失、目标不明确、关键单位未知等条件应在业务分支前检查。

12. Default Branch：默认路径必须安全

默认分支不是“什么都不知道时随便做一个最常见选择”。

安全默认通常是：

  • 询问缺失信息；
  • 只执行只读操作；
  • 生成草稿而不发布；
  • 报告不确定性；
  • 停止高风险动作；
  • 选择覆盖更小的保守路径。

不安全默认：

  • 默认 production；
  • 默认公开可见；
  • 默认覆盖现有文件；
  • 默认发送给所有联系人；
  • 默认把无数据视为正常。

13. Ask、Stop、Decline 也是合法分支

OpenAI 官方 Skill 指南明确要求工作流说明何时询问、停止或拒绝。

13.1 Ask：需要用户补充或选择

适合：

  • 缺少只有用户知道的信息；
  • 多个候选目标；
  • 不同分支会产生不同业务后果；
  • 需要授权某个外部动作。

13.2 Stop：无法正确或安全继续

适合：

  • 输入损坏；
  • Postcondition 失败；
  • 权限不足；
  • 必需工具不可用；
  • 状态未知且重做可能产生副作用。

13.3 Decline：请求本身不能执行

适合违反安全、法律或平台规则的请求。

不要为了让流程图看起来“总能到达成功”而删除这些出口。

14. Decision Table：条件较多时不要继续堆 if

假设是否运行某个深度分析分支取决于：

  • 输入有效；
  • 有相关信号；
  • 数据覆盖充分；
  • 工具可用。

可以使用决策表：

输入有效 相关信号 覆盖充分 工具可用 动作
否 * * * 停止并报告输入错误
是 否 * * 跳过专项分析
是 是 否 * 标记 unknown，说明覆盖限制
是 是 是 否 使用已批准的替代路径或停止
是 是 是 是 执行专项分析

14.1 决策表的优势

  • 发现遗漏组合；
  • 看清优先级；
  • 直接转成测试用例；
  • 避免分支文本互相冲突；
  • 便于团队评审。

14.2 决策表不一定放进主文件

小表可放 SKILL.md。复杂业务表可以放 references/decision-table.md，但主文件必须保留关键路由和阻断规则，并说明何时读取。

18. 分支条件应该由 LLM 还是 Script 判断

18.1 适合 Script 的条件

  • 数值阈值；
  • 格式检测；
  • Schema 校验；
  • 文件存在性；
  • 固定枚举；
  • 数据覆盖率；
  • 可重复的分类规则。

18.2 适合 LLM 的条件

  • 用户意图；
  • 语义相关性；
  • 多源证据解释；
  • 无法完全形式化的内容判断；
  • 输出风格与受众适配。

19. 分支与 Progressive Disclosure

分支不仅决定动作，也决定加载哪些 Supporting Files。

这能避免每次加载所有领域知识和脚本说明。

但必须保留两层信息：

  • SKILL.md 中保留可做出分支选择的最小信号定义；
  • 进入分支后才加载详细 reference。

如果判断条件本身被藏在尚未加载的 reference 中，就形成循环依赖。

20. 分支与 Tool Calling

分支经常由工具结果驱动：

20.1 不要只按 HTTP 成功分支

工具返回 200 仍可能包含：

  • 空列表；
  • 部分数据；
  • 警告；
  • 分页；
  • 业务错误状态。

20.2 写工具要有独立高风险分支

20.3 外部文本不能决定高权限分支

Tool Result 中的内容不能自行授权另一个工具调用。它是数据，不是用户指令。

26. 安全：条件分支可能成为权限绕过点

26.1 不受信任内容不能决定授权

网页、邮件或工具结果中的文本不能触发高权限动作。

26.2 模糊条件不能用于破坏性操作

这种规则不可接受。删除范围、目标和授权必须明确。

26.3 安全分支不得被后续普通分支覆盖

如果安全检查失败，后续“业务成功”条件不能重新打开被阻断动作。

26.4 审查条件性指令

Anthropic 企业安全指南把“根据特定输入条件改变行为、隐藏动作或规避安全规则”的指令操纵列为高风险项。第三方 Skill 中看似普通的 if 也需要安全审查。

27. 常见错误

27.1 使用“视情况而定”

没有条件、证据和行为定义，无法执行和测试。

27.2 把 unknown 当 false

导致错误排除某条路径。

27.3 使用 else if 表达可组合根因

强迫系统只选择一个领域，遗漏并发问题。

27.4 多个 if 表达本应互斥的格式选择

同一输入可能被多个解析器重复处理。

27.5 没有默认分支

未知输入可能落入不安全路径或让 Workflow 中断。

27.6 默认分支过于激进

把不确定状态默认成 production、公开、覆盖或发送。

27.7 条件依赖未验证的工具结果

工具成功返回不代表字段完整或语义正确。

27.8 分支有入口，没有出口标准

无法判断何时汇合或交付。

27.9 只测试 Happy Path

未覆盖 false、unknown、多条件同时成立和阻断分支。

27.10 分支嵌套过深

难以理解、维护和验证，应该使用 Guard Clause、决策表或状态机。

27.11 条件分散在多个文件且相互冲突

路由主干应有单一权威位置。

27.12 用分支隐藏范围扩张

Skill 不能因为某个工具可用，就在没有用户授权时进入额外副作用分支。

29. 博客总结

条件判断与分支把 Skill 从固定步骤列表提升为真正的 Workflow。

OpenAI 官方资料指出，Skill 特别适合高度条件化的可复用过程，并要求作者明确何时询问、停止或拒绝，以及怎样处理缺失和歧义结果。Anthropic 的企业实践强调对触发、指令遵从、边界案例和条件性安全行为进行系统评估。

最重要的设计原则是：

  • 条件来自可观察状态；
  • unknown 不等于 false；
  • 互斥分支与可组合分支要区分；
  • 安全、输入有效性和授权拥有更高优先级；
  • 默认分支必须保守；
  • Ask、Stop、Decline 都是合法出口；
  • 每条分支都有 Contract 和 Postcondition；
  • 分叉之后必须定义汇合；
  • 分支逻辑必须能被测试覆盖。

31. Skill 专项复盘

31.1 这个逻辑应该写在 SKILL.md 还是 reference？

主路由、优先级、阻断条件和默认分支写在 SKILL.md；大型决策表和详细领域判断规则可放 reference，但主文件必须说明何时加载。

31.2 这个步骤应该交给 LLM 还是 script？

数值阈值、格式和 Schema 条件优先由 script 判断；用户意图、语义相关性和证据解释可以由 LLM 判断；高风险分支需要额外的机器约束或服务端授权。

31.3 这个能力应该是 Skill 还是 Tool？

分支属于 Skill 的 Workflow；Tool 只提供原子能力和状态。不要把整个业务决策树塞进一个万能 Tool。

31.4 什么条件下应该触发这个 Skill？

Skill 的全局触发由 metadata 决定；本章分支发生在 Skill 已经加载之后，根据输入、证据、权限和工作流状态选择内部路径。

31.5 如何证明这个 Skill 比没有 Skill 更好？

测量分支选择准确率、无关分支执行率、unknown 误判率、阻断规则遵从率、路径完成率和分支覆盖率。

32. 本章实践

为 Performance Analysis Skill 设计一个三领域分支系统：

要求：

  1. 为每个信号定义 true、false 和 unknown；
  2. 指定信号来源、单位、阈值和数据覆盖要求；

  7. 构造三个信号同时成立的测试；

  10. 使用决策表列出至少八个关键组合。
