2. 三个概念先分清

2.1 Loop：重复执行一个阶段

循环的目标通常是逐步逼近完成条件：

  • 搜索更多证据；
  • 修复验证错误；
  • 分页读取数据；
  • 处理批量对象；
  • 驱动 Tool Call Agent Loop；
  • 迭代生成和审查。

2.2 Retry：重新尝试同一逻辑操作

Retry 通常针对暂时性失败：

  • 网络中断；
  • 限流；
  • 服务过载；
  • 短暂超时；
  • 可解决的并发冲突。

重试的前提是：导致失败的条件可能随时间或参数修正而改变。

2.3 Fallback：切换到替代路径

Fallback 不是再次尝试原路径，而是使用另一个方案：

  • Tool A 不可用，使用 Tool B；
  • 实时数据不可用，使用标明时间的缓存；
  • 专用解析器失败，使用通用解析器；
  • 无法生成图表，交付表格；
  • 高质量路径超出预算，切换到较低成本但合格的路径。

8. Validate–Fix 循环怎样设计

Anthropic Skill 最佳实践强调在质量关键任务中使用验证反馈循环：立即运行验证器、根据具体错误修复、重新验证，只有通过后才能继续。

8.1 修复必须针对错误

不要每轮完全重写全部产物。应使用错误列表定位受影响部分。

8.2 修复后必须从验证器重新开始

模型认为“已经修好”不等于验证通过。

8.3 限制轮数

如果相同错误持续出现，说明自动修复路径失效，应停止并报告。

8.4 错误变化时重新分类

第一次是缺字段，修复后变成文件损坏，不应继续沿用原来的重试策略。

10. Retry 前先分类错误

错误类别 例子 原样重试是否通常有效 正确动作
输入错误 缺参数、Schema 错误 否 修正或询问
认证错误 Token 失效 否 修复凭据
权限错误 无权访问资源 否 请求授权或停止
额度错误 余额、预算耗尽 否 等待外部处理
冲突错误 资源已被修改 有条件 读取最新状态后重建请求
临时错误 限流、超时、过载 是 有界退避重试
工具实现错误 脚本崩溃 通常否 修复实现或 Fallback
语义失败 结果不满足 Contract 原样重试通常否 修改策略或输入

原则：

如果不改变任何条件，同一操作必然再次失败，就不应自动重试。

11. Retryable 与 Non-Retryable

11.1 通常可重试

  • 临时网络失败；
  • 服务器过载；
  • 有明确恢复时间的速率限制；
  • 短暂超时；
  • 服务端标记可重试的错误；
  • 已重新读取状态并修正的并发冲突。

11.2 通常不可原样重试

  • 参数非法；
  • 文件不存在；
  • 凭据错误；
  • 没有权限；
  • 固定大小限制；
  • 账户额度耗尽；
  • 不支持的格式或版本；
  • 安全策略拒绝；
  • 确定性脚本 Bug。

11.3 429 也要分类

有些 429 是短期限流，带 Retry-After；有些可能表示消费上限，等待几秒不会恢复。应依据结构化错误类型和响应头，而不是只看状态码。

12. Retry Budget：重试必须有预算

至少定义：

  • max_attempts：最大尝试次数；
  • max_elapsed_time：最大总时长；
  • retryable_codes：允许重试的错误；
  • backoff：等待策略；
  • stop_on_error_change：错误变化是否停止；
  • fallback_after：何时切换替代方案；
  • on_exhausted：预算耗尽后的行为。

15. Idempotency：安全重试的基础

幂等表示同一个逻辑操作执行多次，最终效果与执行一次相同。

15.1 较容易幂等

  • 读取资源；
  • 将字段设置为确定值；
  • 使用稳定键执行 upsert；
  • 生成到新临时路径。

15.2 通常非幂等

  • 发送邮件；
  • 创建资源；
  • 扣款；
  • 对计数器加一；
  • 追加日志或评论；

19. Fallback 优先级

20. 透明 Fallback

  • 启用了哪个替代方案；
  • 替代结果的时间和来源；
  • 覆盖、精度或能力损失；
  • 哪些结论因此不能成立；
  • 怎样获得完整结果。

27. 如何测试循环

27.1 成功退出

检查完成条件满足后是否立即退出，不再产生额外调用。

27.2 预算退出

目标始终不能满足时，是否在最大轮数、时间或成本处停止。

27.3 无进展退出

连续返回重复结果时，是否检测到没有新信息。

27.4 状态前进

分页 cursor、待处理集合和验证错误数量是否按预期变化。

27.5 恢复

在第 N 轮中断后，是否从检查点继续，而不是从头重复。

27.6 重复检测

是否正确去重来源、对象和副作用。

28. 如何测试 Retry 与 Fallback

28.1 错误分类

  • 400 输入错误不应退避重试；
  • 401/403 不应自动重试；
  • 临时 429 应遵守等待提示；
  • 额度型 429 不应持续重试；
  • 5xx 和超时进入有限重试；
  • 未知错误安全停止。

28.2 重试预算

  • 最大次数精确生效；
  • 总时长截止生效；
  • 错误变化立即停止；
  • SDK 与 Skill 重试没有意外相乘。

28.3 副作用

  • 服务端成功但响应丢失；
  • 回读显示已创建；
  • 同一幂等键重复调用；
  • 状态未知且操作非幂等。

28.4 Fallback

  • 主路径临时失败但重试后恢复，不应过早 Fallback；
  • 主路径确定性不支持，应直接走批准的 Fallback；
  • Fallback 覆盖不足时应降级置信度；
  • Fallback 失败时应停止；
  • 最终输出必须披露替代路径。

28.5 恢复后验证

无论 Retry 或 Fallback 返回成功，都必须重新执行对应 Postcondition 和 Final Check。

29. 常见错误

29.1 无限循环

没有预算和停止条件。

29.2 目标条件主观

无法测试。

29.3 所有错误统一重试

权限、输入和额度问题不会因等待自动消失。

29.4 超时后直接重做写操作

可能制造重复副作用。

29.5 忽略 SDK 自带重试

导致实际调用次数远高于 Skill 声明。

29.6 Fallback 没有明确触发条件

模型可能过早放弃主路径或随意换工具。

29.7 静默 Fallback

用户无法判断数据新鲜度、精度和来源变化。

29.8 Fallback 不做验证

备用路径也可能产生错误或不兼容结果。

29.9 恢复后重新执行已完成工作

浪费资源，并可能重复外部动作。

29.10 把部分成功压成成功或失败

前者隐瞒缺口，后者丢弃已经验证的成果。

29.11 错误变化后仍沿用原重试循环

恢复策略已经失效，需要重新分类。

29.12 达到预算后强行给出确定结论

预算耗尽只说明必须停止，不代表证据已经充分。

30. 博客总结

Loop、Retry 和 Fallback 分别解决不同问题：

OpenAI 官方错误恢复文档强调：重试临时失败前要检查保存状态和已完成副作用，遵守 Retry-After，并设置尝试次数或截止时间。Anthropic 官方文档则明确了工具 Agent Loop 的停止原因、结构化错误反馈、指数退避以及 SDK 已有重试行为。

请记住：

  • 每个循环都有初始状态、进度指标、成功条件和终止条件；
  • 预算耗尽不等于成功；
  • 只有可能变化的错误才适合重试；
  • 重试前先检查副作用；
  • 非幂等写操作不能盲目重做；
  • Fallback 是设计好的替代路径，不是随便换工具；
  • Fallback 的质量损失必须透明；
  • Resume 只继续未完成工作；
  • Retry 或 Fallback 后必须重新验证。

循环主干、停止条件、重试预算、Fallback 触发和失败出口写入 SKILL.md；平台错误码表和大型兼容矩阵可放 reference。

32.2 这个步骤应该交给 LLM 还是 script？

错误分类中的固定规则、预算计数、退避和去重应由代码保障；LLM 可以评估语义证据是否充分、生成修复方案和解释降级影响。

32.3 这个能力应该是 Skill 还是 Tool？

Retry 和 Fallback 的业务策略属于 Skill；Tool 应返回结构化错误、幂等能力和操作状态。不要让 Tool 隐藏无限重试。

32.4 什么条件下应该触发这个 Skill？

Skill 仍由用户目标触发；Loop、Retry 和 Fallback 是 Skill 内部在执行状态、错误类别和证据缺口满足条件时启用的控制流。

32.5 如何证明这个 Skill 比没有 Skill 更好？

测量完成率、平均尝试次数、无进展循环率、重复副作用率、Fallback 正确率、透明披露率、恢复成功率和成本上限遵从率。

33. 本章实践

为一个证据研究 Skill 设计：

  1. 一个最多五轮的搜索循环；
  2. 一个“两轮无新增证据”终止条件；
  3. 一个按 URL 与 claim 去重的状态集合；
  4. 一个 3 次尝试、90 秒截止的 Retry Budget；
  5. 一组 retryable 与 non-retryable 错误；
  6. 一个遵守 Retry-After 的指数退避策略；
  7. 一个写操作超时后的状态确认路径；
  8. 一个主搜索服务到可信缓存的 Fallback Contract；
  9. 一个披露缓存时间和覆盖差异的输出模板；
  10. 一套包含死循环、错误变化、重复副作用和 Fallback 失败的测试。
