Agent Skill 原理与工程实践（十八）：多个 Skill 如何组合与调用

上一章讨论了单个 Skill 内部的循环、重试与 Fallback。但真实任务往往无法由一个 Skill 独立完成。

例如一次系统性能分析，至少可能包含：

表面上看，只要让总 Skill 依次调用几个子 Skill 即可。真正困难的却是：

  • 谁决定调用哪个 Skill；
  • 子 Skill 是提供结果，还是接管后续任务；
  • 上游结果如何变成下游输入；
  • 多个 Skill 能否并行；
  • 某个 Skill 失败后，整体任务如何收敛；
  • 谁负责校验和生成最终答复。

因此，本章严格围绕大纲中的四个概念展开：

1. 先澄清：组合 Skill 不等于拼接 Prompt

一个常见误区是把多个 Skill 的 SKILL.md 全部读入上下文，再让模型“综合执行”。这只是指令堆叠，不是工程意义上的组合。

真正的 Skill 组合至少应明确五种关系：

如果缺少这些边界，常见结果是：

  • 多个 Skill 同时认为自己应该主导任务；
  • 同一份数据被重复分析；
  • 中间结果只有自然语言，无法可靠传递；
  • 子 Skill 修改了不属于自己的状态；
  • 最终报告互相矛盾，却没有组件负责仲裁。

所以，多 Skill 系统的核心不是“多”，而是清楚的控制权、数据契约和责任边界。

2. Skill、Agent 与 Tool 的组合层级

组合之前，必须先区分三个层级：

2.1 Tool 组合

Tool 是一次明确操作，例如读取 trace、解析 JSON、查询指标或生成图表。组合 Tool 主要解决“动作如何执行”。

2.2 Skill 组合

Skill 是带有工作流、约束和领域知识的可复用能力。组合 Skill 主要解决“任务应怎样分解、判断和完成”。

2.3 Agent 组合

多个 Agent 通常意味着不同的模型上下文、工具权限、系统指令或对话所有权。组合 Agent 主要解决“谁来承担哪类角色”。

这三者不能简单画等号：

一个 Agent 可以在同一上下文中依次使用多个 Skill；也可以把某个专门 Agent 包装成工具；还可以把控制权交给另一个 Agent。后两种模式与 Skill 组合相关，但属于运行时编排机制。

3. Orchestration：谁拥有整个流程

Orchestration 是多 Skill 系统的控制平面。它负责：

  • 理解总目标；
  • 分解子任务；
  • 选择 Skill；
  • 建立依赖关系；
  • 调度串行或并行执行；
  • 汇总状态；
  • 处理失败；
  • 验证最终结果。

可以把 Orchestrator 理解为“总导演”，但它不应该亲自完成所有专业分析。

4.1 管理者保持控制权

当子能力只是提供局部结果时，应由主 Skill 或 Orchestrator 保持控制权：

适用于：

  • 最终报告需要综合多个领域；
  • 子任务有清晰的输入输出；
  • 用户只需要一个统一答复；
  • 主流程需要统一控制预算和质量。

4.2 专门能力接管控制权

当任务进入一个独立领域，且后续对话、工具、规则都应由专门角色负责时，可以 handoff：

适用于：

  • 后续步骤需要完全不同的权限或政策；
  • 专门能力需要直接向用户追问；
  • 专门能力应负责其分支上的最终答复；
  • 主 Agent 不应继续充当中间转述者。

不要把 handoff 当作普通函数调用。一旦移交控制权，就必须定义如何返回、是否返回，以及会话状态如何继承。

13. Skill 选择：自动触发与显式编排如何配合

Anthropic 官方文档说明，Skill 在可用环境中会根据任务相关性自动触发；其 metadata 用于发现，完整 SKILL.md 在触发后才加载。这使多个 Skill 可以按需组合，而不必预先把全部正文装入上下文。

但自动触发不等于无需编排。推荐分成两层：

对低风险开放任务，可以让模型动态选择；对高风险或稳定流水线，应显式规定允许的 Skill 集合、调用顺序和退出条件。

13.1 不要挂载所有 Skill

Anthropic 的 Managed Agents 文档明确提醒：挂载更多 Skill 会增加会话沙箱启动时间，应只附加当前 Agent 所需的 Skill。

17. 常见反模式

17.1 God Skill

一个总 Skill 同时包含所有领域知识和全部执行细节。结果是无法复用、难以测试、上下文巨大。

17.2 俄罗斯套娃式委派

子 Skill 随意继续委派，调用深度没有上限。最终无法判断控制权在哪里。

修复：规定最大深度、允许调用列表和返回规则。

17.3 自然语言作为唯一接口

子 Skill 返回散文，下游依靠模型重新理解。结果容易发生字段遗漏、事实升级和解析歧义。

修复：结构化 Envelope + 版本化 Payload。

17.4 把所有上下文广播给所有 Skill

这会增加成本，也会让专业 Skill 越界。修复方法是最小必要上下文和工件引用。

17.5 没有最终结果所有者

多个 Skill 各说一段，却没有组件负责冲突、去重和最终质量。修复：在设计开始时明确最终答复的 owner。

17.6 循环调用

修复：任务图尽量保持 DAG；若业务必须回环，则使用上一章的显式循环状态、进展条件和预算。

17.7 隐藏失败

某个分支失败后，系统仍输出漂亮报告，却不说明证据缺口。这是组合系统最危险的错误之一。

18. 可观测性：记录“为什么调用”，不只记录“调用了什么”

建议每次 Skill 调用产生统一事件：

至少要能回答：

  • 为什么选择这个 Skill；
  • 谁发起了委派；
  • 输入来自哪里；
  • 使用了哪个版本；
  • 是否发生 handoff；
  • 控制权最终回到哪里；
  • 哪个结果影响了最终结论。

否则，一旦最终报告出错，很难判断是路由错误、子 Skill 错误、数据契约错误，还是合并错误。

19. 多 Skill 组合的测试矩阵

单独测试每个 Skill 还不够，还要测试它们的连接处。

19.1 Contract Test

验证上游输出是否满足下游输入 Schema。

19.2 Routing Test

验证不同症状是否选择正确的 Skill，并确保不相关 Skill 不被调用。

19.3 Graph Test

验证依赖顺序、可并行节点和循环检测。

19.4 Partial Failure Test

让一个可选分支失败，检查系统是否继续并披露缺口；让关键上游失败，检查下游是否被阻断。

19.5 Conflict Test

让两个 Skill 返回矛盾结论，验证系统不会静默覆盖。

19.6 Context Isolation Test

验证子 Skill 只能得到完成任务所需的最小上下文和权限。

19.7 Ownership Test

验证 manager 模式下子 Skill 会归还控制权，handoff 模式下新 owner 能正确承接状态。

19.8 Version Compatibility Test

用新旧 Schema 组合运行，确认兼容版本成功、不兼容版本快速失败。

20. 如何判断应该拆成多个 Skill

并不是流程长就必须拆。OpenAI 官方建议只在专业能力能够显著改善能力隔离、政策隔离、Prompt 清晰度或 trace 可读性时增加 specialist；过早拆分会增加 Prompt、trace 和审批面。

可以使用以下判断表：

问题 倾向拆分
是否有独立、可复用的领域目标？ 是
是否需要不同工具或权限？ 是
是否有稳定的输入输出契约？ 是
是否能独立测试和版本化？ 是
是否可能被其他工作流复用？ 是
是否只是同一流程中的两三个简单步骤？ 否
拆分后是否只能互相传递大量隐式上下文？ 否

最稳妥的原则是：

从一个清晰的 Skill 开始，在职责、权限、上下文或输出契约真正发生变化时再拆分。

21. 官方资料带来的工程启示

21.1 OpenAI：先选择控制权模型

OpenAI 将 orchestration 的核心选择归纳为 handoff 与 agents-as-tools。对 Skill 系统而言，这意味着设计者首先要回答：子能力是接管对话，还是只返回有边界的结果？

21.2 OpenAI：专业化必须有实际收益

专业组件应该职责狭窄，描述简短具体；只有当分支真的需要不同指令、工具或政策时才值得拆分。

21.3 Anthropic：Skill 天然支持组合，但依赖渐进加载

Anthropic 将“组合多个 Skill 完成复杂多步骤任务”列为 Skill 的核心价值之一。metadata 常驻用于发现，SKILL.md 和资源按需进入上下文，因此组合不等于一次性加载全部内容。

21.4 Anthropic：可用数量不等于应该全部挂载

平台可以支持很多 Skill，但更多挂载会增加启动成本；应按 Agent 的职责附加必要能力，并把 Skill 来源纳入信任边界。

23. Skill 专项复盘

23.1 这个逻辑应该写在 SKILL.md 还是运行时代码？

角色、路由原则、委派规则、输入输出语义和失败政策写在 SKILL.md；任务图调度、并发、锁、超时、持久化和 Schema 强校验由代码实现。

23.2 子 Skill 应该获得完整会话吗？

默认不应该。传递目标、必要事实、工件引用、约束和输出契约即可。只有 handoff 后需要承接用户交互时，才传递经过筛选的相关历史。

23.3 子 Skill 应该直接回答用户吗？

取决于所有权模型。manager 模式下只返回结构化结果；handoff 模式下可以接管该分支的用户答复。

23.4 什么时候可以并行？

没有数据依赖、写冲突和资源冲突，并且存在明确合并规则时才可以并行。

23.5 如何证明组合设计有效？

测量路由准确率、无效调用率、Contract 通过率、并行加速比、局部失败隔离率、冲突披露率、调用深度、上下文成本和最终任务成功率。

24. 本章实践

围绕 performance-analysis 完成以下设计：

  1. 定义总 Skill 的最终答复所有权；
  2. 为 scheduler、memory、I/O 和 report 四个子 Skill 划定职责边界；
  3. 分别写出输入输出 Schema；
  4. 画出包含数据依赖与条件依赖的 DAG；
  5. 标出可以并行和必须串行的节点；
  6. 为每次委派定义目标、上下文、权限、预算和返回规则；
  7. 设计统一结果 Envelope；
  8. 设计证据去重、关联和冲突处理规则；
  9. 模拟一个子 Skill 部分失败；
  10. 编写 Contract、Routing、Ownership 和 Version Compatibility 测试。
