1. 什么叫“职责重叠”

职责重叠不是两个 Skill 恰好使用了同一个工具，也不是它们都处理同一份 trace。真正的重叠是：

对同一个输入和同一个阶段，多个 Skill 都拥有相同的决策权或交付责任，而系统没有明确的优先级与边界。

例如：

第二个 Skill 名字更具体，但 description 仍然声称可以完成整个性能根因分析。结果可能是：

  • 两个 Skill 同时触发；
  • 总 Skill 绕过专业 Skill 自己分析；
  • 专业 Skill 越界输出整体根因；
  • 两者对最终结果拥有竞争性的控制权。

2. 官方资料给出的两条底层原则

2.1 OpenAI：只有契约发生实质变化时才拆分

OpenAI 官方文档建议从一个职责清晰的 Agent 开始，只有在所有权、指令、工具面、审批策略、模型或输出形式确实不同时，才拆出新的 specialist。

这条原则可以直接迁移到 Skill：

拆分的依据不是文件大小，也不是团队人数，而是契约是否改变。

2.2 Anthropic：description 决定发现，必须测试共存

Anthropic 官方说明，Skill 的 name 和 description 会用于判断是否触发；企业实践还特别要求测试 coexistence，即新增 Skill 是否因为 description 太宽而“抢走”已有 Skill 的触发。

因此，职责边界不是藏在 SKILL.md 正文深处的一句说明。边界必须首先体现在 metadata 中，因为模型在触发前通常只看得到 metadata。

5. 推荐的职责拆分

5.1 performance-triage：分类，不做深度分析

职责：

  • 验证性能问题的基础输入；
  • 识别症状与初始信号；
  • 判断需要调用哪些领域 Skill；
  • 给出分析优先级；
  • 记录证据缺口。

不负责：

  • 宣布某个领域已经是最终根因；
  • 执行深入调度、内存或 I/O 分析；
  • 生成正式报告。

5.3 memory-analysis：只拥有内存领域结论

负责 page fault、reclaim、swap、OOM、内存压力、分配热点和 NUMA 等证据。

遇到 I/O wait 时，只返回 cross_domain_signal，不接管 I/O 分析。

5.4 io-analysis：只拥有 I/O 领域结论

负责设备延迟、队列深度、吞吐、block I/O、文件系统等待等证据。

它不把等待期间观察到的 CPU 行为直接解释为调度根因。

5.5 report-generator：组织已有结论，不创造新结论

负责：

  • 按模板组织内容；
  • 统一术语和格式；
  • 保留证据引用、置信度、冲突与未知项；
  • 生成面向不同读者的报告。

不负责：

  • 自己重新分析原始 trace；
  • 填补缺失证据；
  • 把假设升级成事实；
  • 在冲突结论中擅自选边。

这一条非常重要：格式化职责与分析职责必须分开。

6. 使用“名词 + 动作 + 阶段”检查边界

可以用三个问题检查每个 Skill：

Skill 名词 动作 阶段
performance-triage 性能事件 分类、路由 分析前
scheduler-analysis 调度证据 深度分析 专业分析
memory-analysis 内存证据 深度分析 专业分析
io-analysis I/O 证据 深度分析 专业分析
report-generator 已验证发现 组织、呈现 分析后

如果两个 Skill 在这三列都相同，就应进一步检查是否需要合并。

如果只在名词上不同，但动作和阶段相同，它们可能是并列 specialist；如果名词相同但动作或阶段不同，它们可能是顺序工作流中的不同 Skill。

  • 在什么阶段触发；

10. 决策权必须唯一

工作步骤可以共享，最终决策权不能含糊。

例如多个 Skill 都可以读取时间窗口，但以下权力应有唯一 owner：

  • 谁决定需要哪些领域分析；
  • 谁对调度领域结论定级；
  • 谁决定整体根因；
  • 谁批准执行有副作用的诊断；
  • 谁对最终用户答复负责。

11. 共享工具不等于共享职责

scheduler-analysis、memory-analysis 和 io-analysis 可能都需要：

  • 读取 trace；
  • 计算统计量；
  • 画时间序列图；
  • 查询系统元数据。

这不代表它们职责重叠。Tool 是执行手段，Skill 是领域工作流。

12. 输出所有权比输入范围更重要

多个 Skill 可以读取同一个输入，但最好不要竞争同一个最终输出。

推荐让输出形成分层：

每个输出都有：

  • 唯一 Schema；
  • 唯一生产者或明确优先级；
  • 清晰消费者；
  • 版本和验证规则。

如果两个 Skill 都输出 performance_report_v1，就要解释为什么需要两个生产者。若无法解释，通常说明职责重叠。

15. 出现重叠时，合并还是继续拆分

15.1 应该合并的信号

  • 两个 Skill 的正向触发样例高度相同；
  • 它们使用相同工作流和工具；
  • 输出 Schema 相同；
  • 一个任务经常同时触发二者，但无法说明先后关系；
  • 独立 Eval 无法分别定义成功标准；
  • 维护者总需要同步修改两个 Skill。

15.2 应该保持分离的信号

  • 领域知识显著不同；
  • 工具、权限或安全策略不同；
  • 输入输出契约不同；
  • 可独立复用；
  • 可并行执行；
  • 有不同维护 owner；
  • 任一 Skill 可以替换而不改变另一方。

15.3 应该增加 Router 的信号

  • Skill 本身边界清晰，但用户请求经常模糊；
  • 多数任务只需要其中一个 Skill；
  • 判断依据来自轻量信号；
  • 直接同时触发所有 Skill 成本过高。

注意：增加 Router 不能修复两个内部职责完全相同的 Skill。先解决边界，再解决路由。

17. 用优先级掩盖重叠为什么不够

一种常见做法是：

优先级可以暂时解决选择问题，但无法解决：

  • 两者内部工作流仍然重复；
  • 新增 Skill 后优先级链继续变长；
  • 用户措辞稍变就可能落入错误分支；
  • 被低优先级 Skill 仍占用 metadata 和维护成本。

优先级只适合处理合理的边界接触，不适合替代职责设计。

23. 常见反模式

23.1 名字具体，description 宽泛

scheduler-analysis 的 description 却写“解决所有性能问题”。模型主要依赖 description 触发，具体名字救不了宽泛职责。

23.2 所有 Skill 都能生成最终报告

这会造成多个“最终版本”。应让分析 Skill 输出 finding，让报告 Skill 生成草稿，由 Orchestrator 拥有最终答复。

23.3 每个 Skill 都可以自由调用所有其他 Skill

会形成隐式环路和控制权漂移。应使用允许调用列表、调用深度和 return rule。

23.4 用“必要时”掩盖边界

例如“必要时进行其他领域分析”。谁判断必要、分析到什么程度都不明确。应改成结构化 cross_domain_signal 并交回 Orchestrator。

23.5 新增 Skill，却不回归已有触发

新增一个 description 更宽的 Skill，可能让旧 Skill 的触发率突然下降。每次新增或修改都要运行 coexistence regression。

23.6 拆分过细

如果每个 Skill 只有一个普通步骤，且没有独立契约、复用价值或安全边界，拆分只会增加路由噪声。OpenAI 官方也提醒，过早拆分会增加 Prompt、trace 和审批面。

24. 官方资料带来的工程启示

24.1 OpenAI：先定义最小而清晰的 specialist

一个 specialist 应拥有清楚的任务、约束、工具和输出；只有在所有权、工具、政策或输出确实变化时，才增加新的 specialist。

24.2 OpenAI：路由描述要短而具体

handoff description 的作用是让路由者知道何时选择该能力。对应到 Skill，就是不要用“通用助手”“性能处理”之类抽象描述。

24.3 Anthropic：metadata 是触发边界的第一现场

模型利用 name 和 description 判断何时加载 Skill。正文里的边界如果没有反映到 description，可能在 Skill 被读取之前就已经选错。

24.4 Anthropic：必须评测 Coexistence

官方企业指南明确把“新 Skill 的 description 太宽，抢走已有 Skill 的触发”列为失败示例，并建议在隔离测试之外进行共存测试。发生冲突时，应合并重叠 Skill 或缩窄 description。

26. Skill 专项复盘

26.1 两个 Skill 使用相同 Tool，是否说明重叠？

不一定。共享执行手段很正常，要检查它们的领域解释权、工作阶段和输出所有权是否相同。

26.2 Description 中是否应该写“不做什么”？

对容易与相邻 Skill 混淆的能力，应该写简短排除项；但不要把 metadata 写成完整规则手册。

26.3 如何判断两个 Skill 应合并？

如果它们的触发、流程、工具、输出和成功标准长期相同，并且无法构造稳定的边界 Eval，就应优先合并。

26.4 谁负责跨领域最终根因？

由明确的 Orchestrator 或 correlation Skill 负责。各领域 Skill 只对自己的 finding 负责。

26.5 如何证明职责边界有效？

测量 Trigger Precision、Trigger Recall、Over-trigger Rate、重复工作率、输出所有权冲突、共存回归和人工纠正次数。

27. 本章实践

将一个宽泛的 performance Skill 重构为大纲中的五个 Skill：

  1. 为每个 Skill 写出 Purpose、Trigger、Scope、Authority 和 Deliverable；
  2. 为五个 Skill 分别编写互不竞争的 description；
  3. 建立 Skill Boundary Matrix；
  4. 为每项关键决策指定唯一 owner；
  5. 给每个 Skill 定义唯一输出 Schema；
  6. 定义 scheduler、memory 与 I/O 的交叉信号协议；
  7. 各准备三条 should-trigger、should-not-trigger 与 ambiguous 样例；
  8. 运行 pairwise coexistence 测试；
  9. 检查新增 Skill 是否抢走旧 Skill 的触发；
  10. 把 purpose、owner、version、dependency 和 eval status 记录进 Skill Registry。
