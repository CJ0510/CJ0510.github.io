Agent Skill 原理与工程实践（十三）：scripts/——什么时候 Prompt 不够，需要代码

Agent Skill 原理与工程实践（十三）：scripts/——什么时候 Prompt 不够，需要代码

上一章把 references/ 定位为 Skill 的按需知识层。本章继续按照专题大纲，进入 scripts/：当自然语言指令不足以稳定完成任务时，如何把关键操作固化成可执行代码。

一个 Skill 并不是脚本越多越好，也不是所有步骤都应该交给 LLM。真正的设计问题是：

哪些步骤需要模型的语义理解与灵活判断，哪些步骤需要程序的确定性、可重复性和可验证性？

本章的核心认知是：

1. 这一章要解决什么问题

本章集中回答：

目标不是教某一种编程语言，而是学习如何把脚本设计成 Agent 能可靠调用的确定性组件。

2. 为什么 Prompt 会不够

自然语言指令适合表达目标、约束和决策规则，但它不天然保证每次执行都得到完全相同的过程。

假设在 SKILL.md 中写：

这段指令存在许多隐含问题：

  • 使用哪种分位数算法？
  • 空数据怎样处理？
  • 单位如何统一？
  • 是否忽略非法行？
  • 大文件能否全部放入上下文？
  • JSON 字段是否每次一致？
  • 浮点精度和舍入规则是什么？

模型可能每次采取不同方法，也可能为了完成任务而临时生成一段未经测试的代码。

然后让 Skill 负责：

  1. 判断何时应该计算；
  2. 准备正确输入；
  3. 调用脚本；
  4. 验证脚本结果；
  5. 把结构化结果解释给用户。

3. 整体架构：LLM 决策，Script 执行

这里有一个关键分工：

  • Skill 定义“为什么调用、何时调用、调用后怎么办”；
  • Script 定义“这个具体操作怎样稳定执行”。

脚本不能替代完整 Workflow，Workflow 也不应该反复即兴实现同一个确定性算法。

4. 什么任务适合放进 scripts/

专题大纲列出了四类典型任务：

4.1 计算

例如：

  • 分位数、聚合和统计；
  • 时间单位转换；
  • 哈希与校验和；
  • 差异计算；
  • 图布局坐标；
  • 成本或资源估算。

计算通常要求明确算法和边界行为，比自然语言推算更适合脚本。

4.2 格式转换

例如：

  • CSV 转 JSON；
  • Markdown 转结构化中间表示；
  • 文档解包与重新打包；
  • 图片格式转换；
  • 日志规范化；
  • Schema 版本迁移。

转换规则应保持稳定，脚本也更适合处理大文件。

4.3 校验

例如：

  • JSON Schema 校验；
  • XML/HTML 结构检查；
  • 报告必需字段检查；
  • 链接或引用一致性检查；
  • 数值范围和关系检查；
  • 生成文件能否被重新打开。

验证脚本尤其重要，因为它能把“看起来没问题”变成机器可判定的 Postcondition。

4.4 数据解析

例如：

  • trace 事件解析；
  • 编译器日志提取；
  • PDF 元数据读取；
  • 配置文件解析；
  • 二进制格式解码；
  • 大规模记录过滤。

解析器可以集中处理编码、非法行、版本差异和错误位置。

4.5 稳定重复操作

例如：

  • 生成固定目录结构；
  • 批量重命名；
  • 按统一规则创建报告索引；
  • 规范化日期和标识符；
  • 执行固定的构建与打包流程。

如果同一段逻辑会频繁重复，预置脚本通常比每次重新生成代码更可靠。

5. 判断是否需要脚本：确定性五问

遇到一个工作流步骤时，可以问：

5.1 是否存在唯一或明确算法？

如果是，脚本能减少实现漂移。

5.2 是否需要每次产生同一结构？

稳定的 JSON、CSV、目录或文档结构适合脚本处理。

5.3 是否需要机器验证？

如果成功条件可以写成断言，验证脚本通常很有价值。

5.4 输入规模是否不适合进入模型上下文？

大日志、大数据表和二进制文件应先通过脚本过滤、聚合或转换，再把小而相关的结果交给模型。

5.5 出错代价是否较高？

批量修改、文档重建、迁移和发布前校验需要更低自由度，适合固定脚本和严格参数。

一个简单决策表：

任务 推荐 LLM 推荐 Script
判断用户真正想解决什么 是 否
根据多源证据提出假设 是 辅助
计算 P99 否 是
解析 2 GB 日志 否 是
解释指标意味着什么 是 否
验证 JSON Schema 否 是
选择报告重点 是 否
批量执行格式迁移 规划 是

6. 三种自由度：何时用文字，何时用脚本

Anthropic 官方 Skill 最佳实践提出了一个很有用的视角：根据任务的脆弱性与可变性选择自由度。

6.1 高自由度：自然语言 Workflow

适合：

  • 多种方案都合理；
  • 决策强依赖上下文；
  • 主要依赖启发式判断。

例如代码审查、证据解释和写作结构设计。

6.2 中自由度：参数化模式

适合：

  • 有推荐方法；
  • 允许少量配置；
  • 输入差异需要参数调整。

例如统一的报告生成器，由 Agent 选择格式和是否包含图表。

6.3 低自由度：固定脚本

适合：

  • 操作脆弱；
  • 一致性非常重要；
  • 必须遵守精确顺序；
  • 参数不应随意变化。

例如数据库迁移、文档结构重建和发布前验证。

设计原则是：

自由度应与任务允许的变化程度匹配，而不是所有步骤统一交给 LLM 或统一写成代码。

7. 不要为了“工程化”而滥用脚本

OpenAI 官方文档明确建议：当指令和已有工具已经能够可靠完成任务时，不要额外添加脚本。

以下情况可能不需要脚本：

  • 一次性的简单文本改写；
  • 主要依赖语义判断的审查；
  • 已有 Tool 能直接可靠完成；
  • 代码逻辑比自然语言步骤更复杂，却没有带来稳定性收益；
  • 脚本只是把同一句 Prompt 包在程序里；
  • 不同环境几乎不可能具备其依赖。

反例：

如果当前 Agent 已经能完成总结，这种脚本只是增加了一层不透明调用，并没有提供确定性。

脚本应该真正解决问题，而不是把问题推回给模型。

8. 脚本不是 Tool，也不是 Skill

三者的边界需要明确。

8.1 Script

  • 随 Skill 一起分发；
  • 通常由 Agent 通过 Shell 或执行环境调用；
  • 实现局部、确定性的处理；
  • 自身没有全局触发条件；
  • 通常不负责完整用户交互。

8.2 Tool

  • 是 Agent 可调用的能力接口；
  • 通常具有结构化参数；
  • 可能访问实时数据或执行受控外部动作；
  • 可由多个 Skill 共用。

8.3 Skill

  • 封装某类用户目标的完整工作流；
  • 决定何时调用 Script 或 Tool；
  • 负责输入、输出、分支和成功标准。

可以概括为：

如果一个脚本逐渐变成共享服务、需要权限治理、实时连接和稳定 API，它可能更适合升级为 Tool。

11. SKILL.md 应怎样描述脚本调用

仅写“使用目录中的脚本”远远不够。

11.1 一个完整调用说明

Postconditions:

  • Exit code is 0.
  • artifacts/events.jsonl exists.
  • Every output line is valid JSON.
  • At least one event is present.

On failure:

  • Do not continue to metric calculation.
  • Report the script’s error code and diagnostic message.

12. Plan–Validate–Execute：脚本最重要的工作流模式

对于批量修改、破坏性操作和复杂生成任务，推荐：

例如修改 50 个表单字段：

  1. LLM 根据用户意图生成 changes.json；
  2. scripts/validate_changes.py 检查字段是否存在、类型是否正确、是否冲突；
  3. 只有验证通过后才运行 scripts/apply_changes.py；
  4. 最后运行 scripts/verify_output.py。

这种模式的优势：

  • 修改前发现错误；
  • 中间计划可审查；
  • 验证是机器可重复的；
  • 调试可以定位到具体字段；
  • 在执行副作用之前仍然容易撤销。

14. 错误处理：Script 要解决问题，不要把问题推回给 Agent

Anthropic 官方实践用“solve, don’t defer”概括脚本责任。

这不代表脚本必须吞掉所有错误，而是说它应：

  • 捕获预期异常；
  • 给出具体错误类别；
  • 提供可执行诊断；
  • 清理临时状态；
  • 对部分写入保持谨慎；
  • 不以模糊堆栈信息作为唯一输出。

脚本不应：

  • 遇到任何异常都静默返回空结果；
  • 把失败伪装成成功；
  • 自动猜测关键参数；
  • 在错误后留下半成品却不报告；
  • 要求 Agent 阅读源码才能知道发生了什么。

15.3 不要假设可以运行时安装

不同平台限制不同。Anthropic 官方文档指出，其 API Skill 执行环境没有网络访问，也不能运行时安装新包。因此，Skill 必须确认目标环境是否已经具备依赖。

  • 简单任务优先使用标准库，降低部署风险；

16. 安全：脚本意味着真正的代码执行

脚本比纯 Markdown reference 风险更高。Anthropic 企业安全指南将 Skill 中的可执行脚本列为高风险审查项。

16.1 审查文件访问范围

检查：

  • 是否访问 Skill 目录之外的文件；
  • 是否使用宽泛 glob；
  • 是否允许路径穿越；
  • 是否覆盖用户文件；
  • 是否跟随不安全的符号链接。

16.2 审查网络行为

检查 curl、fetch、requests、urllib 等调用。脚本不应把数据发送到与 Skill 目的无关的目标。

16.3 不硬编码凭据

API Key、密码和 Token 不应进入：

  • 脚本源码；
  • Skill 文件；
  • Git 历史；
  • 错误输出；
  • 生成报告。

16.4 避免 Shell 注入

不要把模型生成的原始字符串拼进 Shell 命令。优先使用参数数组、严格校验和受控枚举。

默认行为应尽可能安全和可恢复。

16.6 第三方 Skill 要审查所有脚本

安装 Skill 应像安装软件一样谨慎，不能只检查 SKILL.md。

17. 脚本输出与上下文效率

Agent 不一定需要读取脚本源码。执行环境可以直接运行脚本，只把输出返回给模型。

这带来两层收益：

  1. 不需要每次在上下文中生成或加载完整代码；
  2. 可以把大输入处理成小而稳定的结构化摘要。

但输出也不能无限大。推荐：

  • 详细结果写入文件；
  • 标准输出返回摘要、状态和产物路径；
  • 只把下一步决策所需信息放入上下文；
  • 必要时支持过滤、分页或采样；
  • 避免输出整个二进制或海量日志。

20. 常见错误

20.1 每次让 LLM 临时生成同一脚本

实现会漂移，且重复消耗上下文和时间。

20.2 脚本只接受隐式输入

依赖当前目录、固定文件名或全局环境，难以复现。

20.3 只输出人类可读文本

Agent 难以稳定提取状态和字段。

20.4 脚本成功但没有 Postcondition

退出码为 0 不代表业务结果正确。

20.5 把所有逻辑都写进一个脚本

解析、计算、写报告和发布耦合在一起，难以独立测试和恢复。

20.6 脚本偷偷猜测关键参数

单位、目标路径和覆盖策略不明确时应报错，而不是静默猜测。

20.7 脚本失败后让 Agent 阅读源码猜原因

应提供结构化、可行动的错误输出。

20.8 运行时下载未知依赖

既可能不可用，也扩大供应链和网络风险。

20.9 使用不受控的 Shell 拼接

模型输入可能变成命令注入载体。

20.10 脚本做了 Skill 应负责的决策

脚本不应悄悄决定用户意图、业务范围或授权边界。

21. 博客总结

scripts/ 是 Skill 的确定性执行层，但并不是所有任务的默认答案。

合理分工是：

OpenAI 官方文档建议仅在需要确定性计算或文件处理时使用 scripts，并强调如果现有指令和工具已经可靠，就不必增加脚本。Anthropic 官方实践进一步强调：脆弱、高一致性、固定顺序的操作应降低自由度；预置脚本比临时生成代码更可靠、更省上下文，也更容易保持一致。

最重要的判断不是“模型能不能写代码”，而是：

这个操作是否值得被实现一次、测试一次，然后在每次 Skill 执行中稳定复用？

23. Skill 专项复盘

23.1 这个逻辑应该写在 SKILL.md 还是 reference？

何时运行脚本、参数如何映射、成功和失败后怎么办写在 SKILL.md；算法背景和字段含义可以写在 reference。

23.2 这个步骤应该交给 LLM 还是 script？

语义理解、范围判断、证据解释交给 LLM；确定性计算、解析、转换和验证交给 script。

23.3 这个能力应该是 Skill 还是 Tool？

局部且随 Skill 分发的确定性操作可作为 script；跨 Skill 复用、需要权限控制或连接外部系统的能力更适合 Tool。

23.4 什么条件下应该触发这个 Skill？

Skill 的触发仍由 name 和 description 决定。脚本没有独立的全局触发，它由 Skill 工作流在满足前置条件时调用。

23.5 如何证明使用脚本比纯 Prompt 更好？

对比正确率、结果一致性、Schema 合规率、执行时间、上下文消耗和边界案例表现，并验证脚本不会引入新的环境与安全风险。
