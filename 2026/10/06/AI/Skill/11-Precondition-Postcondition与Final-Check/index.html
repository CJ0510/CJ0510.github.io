Agent Skill 原理与工程实践（十一）：Precondition、Postcondition 与 Final Check

Agent Skill 原理与工程实践（十一）：Precondition、Postcondition 与 Final Check

一个 Skill 能把步骤写得很完整，却仍然不可靠。

原因通常不是模型不知道“下一步做什么”，而是工作流没有回答三个更重要的问题：

  1. 开始之前，条件真的满足了吗？
  2. 每一步结束后，承诺的状态真的建立了吗？
  3. 最终交付之前，整个结果真的可以放行吗？

这三个问题分别对应：

  • Precondition（前置条件）：当前是否允许开始；
  • Postcondition（后置条件）：动作完成后，哪些事实必须成立；
  • Final Check（最终检查）：完整成果是否满足交付标准。

它们不是装饰性的检查清单，而是 Skill 的三道质量门。

1. 为什么“写清楚步骤”还不够

假设一个 Skill 规定：

  1. 读取性能日志；
  2. 计算 P95 延迟；
  3. 找出慢请求；
  4. 生成优化报告。

步骤看起来很清楚，但仍有大量未定义行为：

  • 日志文件不存在怎么办？
  • 日志只包含表头、没有数据怎么办？
  • 时间单位是毫秒还是微秒？
  • 计算程序退出码为 0，但结果包含 NaN，算成功吗？
  • 报告生成了，但引用的数据来自错误时间范围，能交付吗？
  • 工具调用失败后，模型能不能凭经验补写结论？

如果 Skill 只描述“做什么”，模型很可能把“尝试执行”误当成“成功完成”。

可靠的 Skill 必须把动作和状态连接起来：

2. 三道质量门的职责

质量门 核心问题 发生时机 失败后的典型动作
Precondition 现在可以开始吗？ 动作之前 询问、补齐、降级或停止
Postcondition 这一步真的成功了吗？ 每个关键动作之后 修复、重试、回滚或停止
Final Check 整体结果可以交付吗？ 输出给用户之前 修订、重新验证或拒绝交付

最重要的区别是：

Precondition 控制“是否进入”，Postcondition 控制“是否继续”，Final Check 控制“是否交付”。

2.1 Precondition 不是背景说明

“需要输入文件”只是说明。

“开始分析前，确认输入文件存在、可读、格式受支持；否则停止并说明缺失项”才是可执行的前置条件。

2.2 Postcondition 不是“动作执行过”

“运行分析脚本”是动作。

“脚本退出码为 0，输出 JSON 可解析，sample_count > 0，所有延迟值具有统一单位”才是后置条件。

2.3 Final Check 不是再读一遍结果

最终检查要综合验证：

  • 结果是否满足用户意图；
  • 必需步骤是否都完成；
  • 事实是否有证据；
  • 外部写操作是否真的生效；
  • 是否存在安全、隐私或越权问题；
  • 已知失败和不确定性是否被披露。

4. 如何设计 Precondition

前置条件应覆盖“任务能否安全、正确地开始”，常见可分为六类。

4.1 输入条件

检查输入是否存在、完整、可解释：

这里最后一句很关键：有些事实不能猜。

4.2 环境条件

例如：

  • 所需脚本是否存在；
  • 运行时和依赖是否可用；
  • 当前目录是否正确；
  • 输出目录是否允许写入；
  • 网络或外部服务是否可访问。

环境检查要和任务相关，避免把所有可能依赖都检查一遍。

4.3 工具条件

不仅要确认工具“存在”，还要确认它适合当前输入：

4.4 权限条件

任何产生外部副作用的动作，都要区分：

  • 用户是否授权执行；
  • 当前身份是否具备权限；
  • 目标对象是否明确；
  • 操作范围是否超过用户请求。

“能够调用工具”不等于“已经获得操作授权”。

4.5 安全条件

例如：

  • 目标路径不能是模糊的根目录；
  • 删除、覆盖前必须解析出准确目标；
  • 密钥不能写入报告；
  • 未受信任文本不能被当成 Skill 指令执行。

4.6 业务条件

技术上能执行，并不代表业务上应该执行：

  • 报销单是否处于可审批状态；
  • PR 是否仍然开放；
  • 数据是否属于指定时间区间；
  • 用户选择是否足以确定输出方案。

4.7 前置条件失败时怎么办

不要笼统地写“如果失败则处理错误”。应为不同失败指定策略：

情况 推荐处理
缺少用户才能提供的信息 精确询问
可以安全自动补齐 补齐后重新检查
有可信替代路径 明确降级并说明影响
继续会生成错误结论 停止
继续会产生危险副作用 拒绝执行该动作

5. 如何设计 Postcondition

好的后置条件必须可观察、可判定、与动作直接相关。

5.2 三层后置条件

对于重要步骤，可以同时验证三个层次：

  1. 执行层：工具是否正常结束；
  2. 结构层：输出是否可解析、字段是否齐全；
  3. 语义层：内容是否真的满足业务含义。

5.4 后置条件要局部化

每一步只验证自己负责建立的状态。例如：

  • 解析步骤负责输出结构化数据；
  • 统计步骤负责指标正确；
  • 写作步骤负责报告结构和引用；
  • 发布步骤负责目标位置和发布状态。

如果所有验证都拖到结尾，错误来源会很难定位，修复成本也更高。

6. Invariant：执行过程中始终不能被破坏的约束

Precondition 和 Postcondition 描述动作前后；Invariant（不变量）描述整个工作流执行期间都必须成立的约束。

常见不变量包括：

  • 原始输入文件保持不变；
  • 所有事实结论都能追溯到证据；
  • 不向输出泄露密钥或隐私数据；
  • 不操作用户未指定的资源；
  • 不把“无数据”写成“指标为零”；
  • 不把工具失败写成业务结论。

7. Final Check：交付前的整体放行门

最终检查的任务不是重复所有步骤，而是确认完整成果可以交付。

一个通用的 Final Check 可以包含七个维度。

7.1 结构完整性

  • 必需文件是否存在；
  • 必需章节、字段、附件是否齐全；
  • 文件格式是否可打开、可解析。

7.2 语义正确性

  • 结论是否回答了用户的问题；
  • 计算关系是否合理；
  • 不同部分是否互相矛盾；
  • 建议是否由分析结果支持。

7.3 证据与可追溯性

  • 事实是否附带来源；
  • 引用是否真的支持对应论断；
  • 数据、工具输出和最终结论之间是否可追踪；
  • 推断是否明确标注为推断。

7.4 流程合规性

  • 必须执行的步骤是否真的执行；
  • 规定的验证器是否运行；
  • 是否出现跳过检查却宣称完成的情况。

7.5 安全与隐私

  • 是否泄露敏感信息；
  • 是否写入越权位置；
  • 是否包含危险命令或未经确认的破坏性操作；
  • 是否将不可信内容作为指令传播。

7.6 副作用确认

  • 外部资源是否创建在正确位置；
  • 更新目标是否准确；
  • 变更是否已被回读确认；
  • 部分成功是否被如实报告。

7.7 用户意图对齐

  • 交付格式是否正确；
  • 范围是否超出或遗漏；
  • 是否遵守用户明确约束；
  • 结果是否适合用户预期的阅读或使用方式。

8. Final Check 不能替代过程验证

一种常见错误是：先完成全部工作，最后统一检查。

这会造成两个问题：

  1. 错误沿着工作流传播；
  2. 到最后才发现问题，无法判断由哪一步引入。

更可靠的策略是 Shift-left Validation（验证左移）：

Final Check 是系统级验收，不是对局部 Postcondition 的替代。

可以类比软件测试：

  • Postcondition 类似单元级或步骤级断言；
  • Final Check 类似集成测试和验收测试。

9. 机器验证、模型检查和真实执行

不同问题需要不同验证手段。

9.1 优先使用机器验证

适合机器验证的内容：

  • JSON/YAML/Markdown 格式；
  • Schema；
  • 文件是否存在；
  • 测试是否通过；
  • 链接和引用字段是否完整；
  • 数值范围和关系；
  • 禁止字段或敏感模式。

Claude 官方的 Skill 最佳实践明确建议形成验证循环：运行验证器、修复错误、再次运行，直到通过。OpenAI 关于 Skill 评估的实践也强调把“完成定义”和必须遵守的工作流步骤转化为可测断言。

9.2 模型检查适合语义问题

例如：

  • 解释是否清楚；
  • 建议是否与证据一致；
  • 是否遗漏用户的关键约束；
  • 文档是否适合目标读者。

但“让模型自己觉得不错”不是强验证。应该提供明确、可反驳的检查问题：

9.3 可执行成果需要真实运行

代码、命令、构建、数据转换不能只靠静态阅读：

  • 运行测试；
  • 执行构建；
  • 解析生成文件；
  • 必要时在隔离环境中运行；
  • 对真实输出做断言。

“代码看起来正确”不是 Postcondition。

12. 代码修改 Skill 的检查设计

对于代码工作，三道门可以这样设计。

Precondition

  • 明确目标仓库和工作目录；
  • 检查现有未提交改动，避免覆盖用户工作；
  • 识别项目指令和测试命令；
  • 确认修改范围和禁止触碰的模块；
  • 对破坏性操作取得明确授权。

每步 Postcondition

  • 补丁准确应用到目标文件；
  • 修改后的文件可解析；
  • 相关静态检查通过；
  • 聚焦测试通过；
  • 失败输出被保留并用于定位，不被忽略。

Final Check

  • 查看最终 diff，确认没有无关改动；
  • 运行与风险相称的测试；
  • 检查接口、文档、迁移和兼容性影响；
  • 确认没有密钥、调试代码或临时文件；
  • 向用户说明已验证内容和尚未验证的内容。

注意：“所有测试通过”也不一定足够。如果测试范围没有覆盖用户请求，Final Check 仍然不能放行。

13. 检查矩阵：把条件变成工程资产

对于复杂 Skill，可以用检查矩阵统一管理。

ID 阶段 条件 验证方式 失败处理 是否阻断
PRE-01 开始前 输入文件可读 文件检查 请求正确路径 是
PRE-02 开始前 时间单位明确 元数据解析 询问用户 是
POST-01 解析后 JSON 符合 Schema 验证脚本 修复或停止 是
POST-02 统计后 P50 ≤ P95 ≤ P99 数值断言 停止并报告 是
FINAL-01 交付前 每条结论有证据 引用检查 修订报告 是
FINAL-02 交付前 建议覆盖用户问题 语义检查 修订报告 是
FINAL-03 交付前 限制已披露 清单检查 补充说明 是

它带来三个好处：

  1. 条件有唯一标识，便于日志和错误报告；
  2. 验证方式与失败策略不再隐藏在散文中；
  3. 可以直接转化为 Skill eval 的测试用例。

14. 如何为三道质量门编写 Eval

OpenAI 的 Skill 评估实践强调：不仅要检查最终答案，还要检查 Skill 是否被触发、规定流程是否被遵守，以及“完成定义”是否满足。

14.1 Precondition 测试

准备输入不完整的案例：

  • 没有文件；
  • 单位不明确；
  • 路径不可读；
  • 用户要求修改未授权目标。

期望行为不是“尽力生成结果”，而是正确询问、降级或停止。

14.2 Postcondition 测试

让工具返回各种伪成功：

  • 退出码为 0，但输出为空；
  • JSON 可解析，但必需字段缺失；
  • 指标包含 NaN；
  • API 返回成功，但回读状态不一致。

检查 Skill 是否阻止流程继续。

14.3 Final Check 测试

构造局部都合法、整体却不合格的结果：

  • 报告结构完整，但回答错了时间范围；
  • 每个指标都合法，但建议与指标无关；
  • 文件已生成，但写到了错误目录；
  • 结果正确，却遗漏工具失败和不确定性。

这类测试能验证 Final Check 是否真正承担系统级验收职责。

15. 常见反模式

15.1 只在最后验证

错误中间状态已经污染后续步骤，定位和修复都更困难。

15.2 Checklist Theater

写了很多“确认、确保、检查”，却没有验证方法、失败分支和阻断规则。

15.3 使用主观条件

这种条件不可复现。应转化为结构、证据、范围和读者适配等明确维度。

15.4 Postcondition 与动作同义

“生成文件后，确认文件已生成”过于弱。还要验证格式、内容、位置和语义。

15.5 混淆无数据、失败和零值

  • 无数据：没有可计算样本；
  • 失败：工具未能完成计算；
  • 零值：成功测得结果为 0。

三者必须使用不同状态表达。

15.6 Final Check 修改结果后直接交付

任何修订都可能引入新问题，必须重新验证受影响部分。

15.7 无限重试

没有上限、没有错误分类、没有退出条件的重试，会让 Skill 陷入循环。

16. 一份可复用模板

17. 本章练习

选择一个你熟悉的 Skill，例如“代码审查”“论文总结”或“生成周报”，完成以下任务：

  1. 写出 5 个 Precondition，并标注哪些是阻断条件；
  2. 为每个关键动作设计至少一个结构后置条件和一个语义后置条件；
  3. 写出 3 个贯穿全流程的 Invariant；
  4. 设计一份包含结构、语义、证据、安全和用户意图的 Final Check；
  5. 为每一种失败指定“询问、修复、重试、降级或停止”中的一种策略；
  6. 构造一个“工具表面成功、实际结果错误”的 Eval 用例。

完成后，尝试回答：

如果某个条件无法通过工具、脚本或明确规则验证，它究竟是必要的质量条件，还是一句无法执行的愿望？

18. 本章小结

一个可靠 Skill 不只是告诉 Agent 如何行动，还要定义行动前后的可验证状态。

请记住：

  • Precondition 决定是否能开始；
  • Postcondition 决定某一步是否真的成功；
  • Invariant 保护执行全过程；
  • Final Check 决定完整成果能否交付；
  • 验证应尽可能左移，并优先使用机器可执行的断言；
  • 每个失败检查都需要明确、有限且安全的处理分支；
  • 最终答案不是因为“已经生成”而合格，而是因为“已经通过放行条件”才合格。
