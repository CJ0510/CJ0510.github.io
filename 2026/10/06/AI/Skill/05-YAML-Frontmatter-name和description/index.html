20. Precision和Recall

Precision低通常意味着误触发多，Description可能太泛；Recall低通常意味着漏触发多，Description可能太窄或缺少重要表达。

实际工程还要考虑错误成本。有副作用的Skill应特别控制False Positive，并结合权限、确认和服务端规则，而不能只依赖Description。

22. 版本与安全

name应尽量稳定，因为用户、文档、Eval、日志和其他Skill可能引用它。description可以迭代，但修改Description相当于修改路由逻辑：

Description同样属于安全边界，但不能独自保证安全。关键限制必须同时落实在Skill正文、Tool权限、API凭证、服务端授权、用户确认和审计系统中。

23. Review Checklist

Name

  • 是否具体、稳定？
  • 是否采用统一命名风格？
  • 是否避免helper、utils、general等模糊词？
  • 是否避免版本号和实现细节？
  • 是否满足目标平台格式要求？

Description

  • 是否说清做什么和什么时候使用？
  • 是否围绕用户目标？
  • 是否包含关键对象或输入？
  • 是否与相邻Skill可区分？
  • 是否需要负向边界？
  • 是否避免完整Workflow和关键词堆砌？
  • 是否覆盖非技术用户的常见表达？
  • 是否用正向和负向样例测试过？

集合层

  • 是否有两个Skill描述几乎相同？
  • 是否存在无人负责的任务区域？
  • 是否有多个Skill争抢入口？
  • 父Skill和子Skill阶段边界是否明确？
  • 修改一个描述后是否重新测试整个Skill集合？

24. 本章实践

将下面三个描述分别改造成performance-triage、scheduler-analysis和trace-validation：

每个Description都需要包含：

  1. 做什么；
  2. 使用什么对象或证据；
  3. 什么时候触发；
  4. 与另外两个Skill的边界。

然后为每个Skill写3条正向请求、3条负向请求和1条边界请求。

25. 学完检查题

  1. 为什么正文写得很好，Skill仍可能完全没有效果？
  2. name和description分别承担什么职责？
  3. Description为什么不是产品宣传语？
  4. 为什么“做什么”和“什么时候用”都必须出现？
  5. 为什么不应把整个Workflow塞进Description？
  6. 什么情况下需要负向边界？
  7. 为什么多个Skill的Description要作为集合一起评审？
  8. Precision低和Recall低分别可能说明什么？
  9. 为什么修改Description应运行回归测试？
  10. 有副作用的Skill能否只通过Description保证安全？

26. 本章总结

name是Skill的稳定身份，description是Skill的语义路由规则。模型在读取完整工作流之前，必须先依靠它们判断Skill是否与用户目标相关。因此Frontmatter不是装饰性元数据，而是Skill执行链的第一道控制面。好的Description应描述能力、对象、触发条件和必要边界，并通过正向、负向和相邻任务样例持续评测。
