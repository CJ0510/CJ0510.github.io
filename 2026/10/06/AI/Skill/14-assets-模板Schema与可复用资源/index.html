这会产生几个问题。

2.1 格式容易漂移

即使描述很详细，模型仍可能改变标题、字段顺序、表格列和固定声明。

2.2 大量固定内容占据主指令

模板本身并不是 Workflow，却挤压了真正的步骤和约束。

2.3 每次重新生成相同骨架

相同的报告结构、配置或品牌元素被反复创建，增加成本和差异。

2.4 机器资源不适合嵌入自然语言

JSON Schema、配置样例、图像、字体和文档模板不应该被全部展开到 SKILL.md。

2.5 资源与指令难以独立升级

公司更换 Logo 或报告版式时，不应同时修改工作流逻辑。

3. 整体架构：Asset 是工作流的输入材料

OpenAI 官方文档把 assets/ 定义为工作流应复制或转换的模板和文件，并将它与 references/ 的背景材料、scripts/ 的确定性操作区分开。

4. assets/ 适合放什么

4.1 报告模板

例如：

  • Markdown 报告骨架；
  • HTML 页面模板；
  • DOCX 文档模板；
  • PPTX 母版；
  • 邮件模板；
  • Issue 或 PR 描述模板。

模板提供稳定结构，模型负责根据任务内容填充和适配。

4.2 JSON / YAML Schema

例如：

  • 最终报告 Schema；
  • 中间计划文件 Schema；
  • 配置 Schema；
  • Tool 结果的本地验证 Schema；
  • 数据交换格式。

当 Schema 被验证器直接读取时，它是机器资源，适合放在 assets/。

4.3 配置文件

例如：

  • 默认阈值；
  • 允许的枚举值；
  • 渲染选项；
  • 导出设置；
  • 项目默认布局。

配置文件应提供可解释的字段和安全默认值，而不是隐藏决策。

4.4 Prompt Template

某些 Skill 会把一段固定模板交给下游模型、分类器或生成步骤使用。这类模板可以作为 asset，但必须明确：

  • 谁使用；
  • 在工作流哪一步使用；
  • 可替换变量；
  • 哪些文本不可修改；
  • 输出怎样验证。

不要让 Prompt Template 与 SKILL.md 的顶层指令发生冲突。

4.5 示例输出

示例输出可以帮助保持风格和结构，例如：

但它与 reference 中的教学示例有所不同：作为 asset 的示例通常会被复制、改写或作为生成基线；作为 reference 的示例主要供 Agent 理解判断方法。

4.6 品牌与媒体资源

例如：

  • Logo；
  • 图标；
  • 配色表；
  • 字体；
  • 页眉、页脚；
  • 背景图片；
  • 预制图表主题。

4.7 代码或项目骨架

例如：

  • 配置文件模板；
  • 最小项目目录；
  • CI Workflow 模板；
  • Dockerfile 基础模板；
  • 示例测试夹具。

如果资源要被复制后再编辑，它通常比自然语言 reference 更像 asset。

13. 示例输出：参考、模板还是测试夹具

同一个示例文件可能承担不同角色，需要明确。

13.1 作为 Reference

Agent 阅读它，学习表达方式或判断逻辑。

13.2 作为 Asset Template

Agent 复制它，并替换其中内容。

13.3 作为 Golden Fixture

测试程序将实际输出与它比较。

这三种角色不应混在同一个文件中，否则：

  • Agent 可能复制本应只供理解的数据；
  • 测试样例可能被任务执行覆盖；
  • 示例中的虚构事实可能进入最终报告。

15. 版本管理与兼容性

15.1 Asset 与 Workflow 要兼容

如果 SKILL.md 要求 {{root_cause}}，模板却已改成 {{diagnosis}}，工作流会失败。

可以记录：

15.2 Schema 演进

区分：

  • 新增可选字段：通常向后兼容；
  • 删除字段：可能破坏旧脚本；
  • 重命名字段：需要迁移；
  • 改变类型：高风险；
  • 加强约束：可能让旧产物失效。

15.3 资源更新要进入回归测试

只改模板没有改代码，也可能破坏：

  • 解析器；
  • 验证器；
  • 文档布局；
  • 占位符替换；
  • 下游消费系统。

15.4 不依赖“latest”语义

生产工作流应尽量让资产版本与 Skill 版本一起发布，确保一次运行使用的是一致快照。

OpenAI 官方 Skills 文档指出上传后的 Skill 使用版本化 bundle，这也体现了 supporting files 与 Skill 版本保持一致的重要性。

16.2 验证可打开性

16.3 检查嵌入内容

16.4 许可证

字体、图片、图标和品牌素材可能有使用限制。Skill 的可执行性不等于资源具备分发许可。

17. 安全：模板注入与路径风险

17.1 模板内容也可能包含指令

如果 Asset 来自不可信来源，其中可能嵌入让 Agent 忽略规则、读取隐私文件或外传数据的文本。应把它视为待处理数据，而不是高优先级指令。

17.2 输出路径必须受控

模板变量不能直接决定任意文件路径。需要：

  • 规范化路径；
  • 限制输出根目录；
  • 拒绝 ../ 穿越；
  • 明确覆盖策略；
  • 避免用户输入成为绝对路径。

17.3 转义不同输出格式

  • HTML：防止标签和脚本注入；
  • JSON：正确转义引号和控制字符；
  • YAML：处理类型歧义；
  • Shell：不要直接拼接；
  • Markdown：注意链接和嵌入内容。

17.4 敏感数据不能进入可复用资产

模板、默认配置和示例不应包含：

  • 真实密钥；
  • 客户隐私；
  • 内部 Token；
  • 生产环境地址和凭据；
  • 未脱敏的真实案例。

18. 验证 Asset 驱动的输出

18.1 结构验证

  • 必需章节存在；
  • 必需字段存在；
  • 字段类型正确；
  • 标题层级正确；
  • 文件可以解析。

18.2 完整性验证

  • 必填占位符全部替换；
  • 没有 TODO/TBD；
  • 可选部分要么正确填充，要么完整移除；
  • 没有从示例遗留的虚构数据。

18.3 语义验证

  • 数据与分析结果一致；
  • 字段没有被填到错误位置；
  • 结论有证据；
  • 配置值符合当前任务范围。

18.4 视觉验证

对于 PPTX、DOCX、PDF、HTML 和图片类输出，还应渲染后检查：

  • 内容是否溢出；
  • 字体是否丢失；
  • 图像是否变形；
  • 页眉页脚是否遮挡；
  • 表格是否截断；
  • 品牌元素是否正确。

18.5 源资产不变验证

任务结束后确认模板和原始资源没有被意外修改。

20. 如何测试 assets/

20.1 文件存在性测试

检查 SKILL.md 引用的每个 Asset 都存在，路径大小写和目录结构正确。

20.2 模板 Contract 测试

  • 必需占位符是否齐全；
  • 是否有重复或未声明变量；
  • 固定区块是否存在；
  • manifest 与模板是否一致。

20.3 Schema 测试

至少提供：

  • 一个合法样例；
  • 缺少必填字段的非法样例；
  • 类型错误样例；
  • 多余字段样例；
  • 边界值样例。

20.4 Round-trip 测试

20.5 不可变性测试

运行 Skill 前后比较源 Asset 的哈希，确认任务执行没有污染模板。

20.6 多模型测试

不同模型可能对柔性模板和占位符规则理解不同。应在计划使用的模型上检查：

  • 是否选择正确模板；
  • 是否保持固定结构；
  • 是否填完所有变量；
  • 是否过度复制示例文本。

21. 常见错误

21.1 把 Asset 当 Reference 使用

只让 Agent 阅读模板，却没有告诉它复制、填充或转换。

21.2 把 Reference 当 Asset 复制

将解释文档直接复制进最终产物，造成结构和内容污染。

21.3 模板变量没有 Contract

Agent 不知道哪些必填、类型是什么、如何转义。

21.4 直接修改源模板

下一次任务会从已污染的模板开始。

21.5 固定与可变部分没有标注

模型可能修改法律声明，也可能机械保留应该按任务调整的部分。

21.6 把真实数据放进示例

隐私数据可能随 Skill 分发，示例事实也可能泄漏到最终输出。

21.7 Schema 与说明文档不同步

模型按 reference 生成，验证器按另一个规则拒绝。

21.8 只检查文件是否生成

文件存在不代表可解析、可渲染或符合模板约束。

21.9 提供太多相似模板却没有选择规则

Agent 会随机选择或错误合并。

21.10 把动态信息写死在 Asset

日期、价格、API 当前行为和实时状态很快过期，应在执行时获取。

22. 博客总结

assets/ 是 Skill 的可复用资源层。

OpenAI 官方文档明确将 assets 定位为工作流要复制或转换的模板与文件，并建议从 SKILL.md 说明何时使用 supporting files。Anthropic 官方资料则强调根据任务需要选择严格或柔性的模板结构，并通过按需资源支持 Progressive Disclosure。

设计 Asset 时最重要的问题不是“这个文件是否可复用”，而是：

工作流会不会把它作为材料复制、填充、组合或转换成最终产物？

如果答案是“只需要阅读和理解”，它更可能属于 reference；如果答案是“要执行”，它更可能属于 script。

24. Skill 专项复盘

24.1 这个逻辑应该写在 SKILL.md 还是 reference？

Asset 的选择时机、填充规则和验证要求写入 SKILL.md；字段语义和背景说明可以放 reference；真实模板放 asset。

24.2 这个步骤应该交给 LLM 还是 script？

选择模板和生成语义内容可以由 LLM 完成；严格变量替换、Schema 校验、格式转换和渲染检查可交给 script。

24.3 这个能力应该是 Skill 还是 Tool？

Asset 不是能力，它是文件资源。如果需要从外部系统实时获取或管理模板，相关操作可能成为 Tool，但使用这些模板完成用户目标的流程仍由 Skill 定义。

24.4 什么条件下应该触发这个 Skill？

Asset 不参与全局 Skill Discovery。Skill 触发后，根据报告类型、输出格式、受众和工作流状态选择 Asset。

24.5 如何证明使用 Asset 比纯 Prompt 更好？

比较结构一致性、占位符完成率、Schema 合规率、视觉质量、生成成本和品牌规范遵从，并检查模板选择错误率。

  5. 让输出写入 artifacts/，不修改源模板；
  6. 验证没有残留占位符；
  7. 检查 Schema、模板说明和脚本之间是否一致；
  8. 运行一次完整的复制、填充、验证和渲染流程。
