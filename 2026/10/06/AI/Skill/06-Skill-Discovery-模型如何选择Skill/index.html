  • 不使用相互冲突的术语。

6. 一个实用的语义匹配模型

可以把Skill选择抽象成一个非确定性的相关性评分：

这不是官方公布的内部算法，也不代表平台真实实现，而是用于设计和调试的工程模型。

6.1 Goal Match

用户是想诊断、生成、审查、解释，还是修改？

6.2 Object Match

对象是PDF、PR、调度Trace、数据库还是事故报告？

6.3 Input Match

用户提供了日志、Trace、指标、文档还是源代码？

6.4 Output Match

用户想得到诊断报告、修改后的文件、摘要还是操作结果？

6.5 Stage Match

当前处于分诊、专项分析、汇总还是最终校验阶段？

6.6 Boundary Conflict

是否命中了明确的排除条件，例如“不要用于现有项目修改”？

6.7 Competing Skill Advantage

是否有另一个Skill对当前目标描述得更精确？

8. Skill选择中的四类错误

类型 含义 示例
True Positive 应触发且触发 用trace诊断调度延迟
False Positive 不应触发却触发 一般概念问答触发诊断Skill
False Negative 应触发却未触发 提供trace求诊断但Skill未加载
True Negative 不应触发且未触发 写诗没有触发性能分析

8.1 False Positive的代价

  • 加载无关上下文；
  • 浪费Token和时间；
  • 调用不必要工具；
  • 修改不该修改的文件；
  • 抢占其他Skill的触发；
  • 对有副作用任务造成安全风险。

8.2 False Negative的代价

  • 丢失关键Workflow；
  • 漏掉必需检查；
  • 输出格式漂移；
  • 重复要求用户说明规范；
  • 无法调用Skill内的脚本和资源。

9. 为什么会漏触发

9.1 Skill根本没有被宿主发现

可能原因：

  • 放错目录；
  • 目录层级不符合扫描规则；
  • SKILL.md命名错误；
  • YAML无效；
  • Skill没有附加到Agent或Session；
  • 运行环境没有读取权限。

9.2 Description太窄

用户说“线程唤醒后很久没运行”，虽然语义相关，却没有明显命中技术字段。

9.3 Description只写输入，不写目标

Trace可以用于解析、可视化、诊断、转换和归档，目标不明确。

9.4 用户请求信息不足

如果附件、上下文和任务目标都不明确，模型无法稳定路由。

9.5 相邻Skill描述更强

本来应该使用performance-triage，但general-debugging写了极宽的描述，可能抢走触发。

10. 为什么会误触发

10.1 Description过于宽泛

它可能匹配性能理论、Benchmark、代码优化和事故诊断等完全不同任务。

10.2 关键词堆砌

缺少任务关系和边界，会对大量请求产生弱匹配。

10.3 Name过于通用

显式引用和语义选择都缺乏辨识度。

10.4 没有表达Workflow阶段

performance-report如果只写“处理性能问题并生成报告”，可能在证据收集前就被选中。更好的描述是“在诊断完成并已有证据后生成报告”。

10.5 没有负向边界

创建新项目和修改现有项目的任务共享大量关键词。如果Scaffold Skill不写“仅用于新项目”，就容易误触发。

13. 显式调用和自动选择

13.1 显式调用

用户直接指定：

优点：

  • 降低路由不确定性；
  • 便于调试和复现；
  • 适合Eval；
  • 适合专家用户。

但显式调用仍不能绕过：

  • 更高优先级的安全规则；
  • 工具权限；
  • 输入前置条件；
  • 用户确认要求；
  • 运行环境限制。

13.2 自动选择

用户只描述自然目标，模型根据Catalog选择Skill。它更符合普通用户体验，但需要更好的元数据和更完整的Trigger Eval。

15. Discovery与安全边界

被宿主发现的Skill并不只是“可搜索文档”，而是可能进入Agent执行路径的指令和代码。

风险包括：

因此Skill来源和扫描目录属于信任边界。需要：

  • 只扫描受信目录；
  • 审查仓库中的Skill变更；
  • 限制脚本和Tool权限；
  • 对外部贡献执行安全审查；
  • 记录使用的Skill及版本；
  • 对有副作用能力要求确认；
  • 不把Description当成安全控制。

Claude官方特别提醒，挂载仓库中的Skill可能被仓库贡献者修改，并在Session启动时进入Agent可用指令集合，因此挂载仓库本身属于Agent信任边界。

16. Discovery调试顺序

当Skill没有按预期触发时，按下面顺序排查：

第一步：确认宿主发现

第二步：确认元数据可见

第三步：测试显式调用

如果显式调用也失败，问题可能在安装、路径、权限或正文加载，而不是语义路由。

第四步：测试最小隐式请求

使用最典型、不带噪声的请求。如果仍不触发，说明Description覆盖不足或存在竞争。

第五步：加入相邻Skill

单独测试通过后，与完整Skill集合一起测试，检查Coexistence和Trigger Stealing。

第六步：查看执行Trace

确认模型是否看到Catalog、是否读取SKILL.md、是否选择另一个Skill、是否因前置条件放弃执行。

19. 改进Discovery的工程策略

19.1 先定义Use Case，再写Description

不要先写一个宽泛名字再寻找用途。应先列出：

19.2 使用真实用户语言

Description既要包含领域术语，也要覆盖用户对现象的自然表达。

19.3 让父子Skill按阶段区分

不要让父Skill和子Skill使用相同的触发描述。

19.4 控制Skill粒度

过大Skill边界模糊，过小Skill导致Catalog拥挤。合理粒度通常对应一个稳定用户目标和一套共同成功标准。

19.5 每次新增Skill都运行全量Trigger Eval

只测试新Skill自己是不够的。必须检查它是否改变旧Skill的路由行为。

21. Discovery Review Checklist

Host Discovery

  • Skill是否位于宿主扫描位置？
  • 目录深度和文件名是否正确？
  • Frontmatter是否可解析？
  • Skill是否已附加或启用？
  • 运行环境是否有读取权限？

Metadata

  • name是否稳定且具体？
  • description是否同时包含What和When？
  • 是否说明输入、目标和必要边界？
  • 是否覆盖自然语言表达？
  • 是否避免关键词堆砌？

Coexistence

  • 是否与现有Skill高度重叠？
  • 父子Skill是否按Workflow阶段区分？
  • 是否可能发生Trigger Stealing？
  • 新增后是否重新测试全部Skill？

Evaluation

  • 是否有显式、隐式和上下文正向样例？
  • 是否有负向和模糊边界样例？
  • 是否记录Primary、Secondary和Forbidden Skills？
  • 是否测试所有计划使用的模型？
  • 是否保存失败样例用于Regression？

Security

  • Skill来源是否可信？
  • 扫描目录是否属于受控仓库？
  • 是否审查脚本和引用文件？
  • 是否使用最小Tool权限？
  • 高风险动作是否需要确认和服务端授权？

24. 本章总结

Skill Discovery包含宿主扫描与模型语义选择两个层次。宿主负责找到、验证并暴露Skill元数据，模型再根据用户目标、任务对象、输入、输出和工作流阶段选择零个、一个或多个Skill。Discovery质量是整个Skill集合的属性：新增一个描述过宽的Skill，可能抢走已有Skill的触发。因此，Skill不仅要单独测试，还必须进行共存测试、负向测试和全量回归。
