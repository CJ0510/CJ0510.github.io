Agent Skill 原理与工程实践（十二）：references/——什么时候该把知识拆出去

前面几章已经完成了 Skill 的核心工作流设计：输入、输出、步骤、前置条件、后置条件和最终检查。

接下来会遇到一个非常实际的问题：

领域知识、规范、Schema、示例和 API 说明越来越多，是否应该全部写进 SKILL.md？

答案通常是否定的。

SKILL.md 的主要职责是保存工作流主干，references/ 的主要职责是保存执行工作流时按需查阅的知识。合理拆分之后，Agent 不需要在每次触发 Skill 时都加载全部资料，只需在进入特定任务分支时读取相关文件。

本章将建立以下核心认知：

1. 这一章要解决什么问题

本章集中回答：

目标不是机械地创建一个 references 目录，而是建立一套知识分层与按需加载机制。

2. 为什么需要 references/

假设我们正在编写一个 Performance Analysis Skill。最初的 SKILL.md 可能只有：

随着功能增加，我们又加入：

  • Linux scheduler 各类事件的含义；
  • 内存回收指标解释；
  • block I/O 延迟分析方法；
  • 不同内核版本的字段差异；
  • 报告 Schema；
  • 根因判断准则；
  • 若干完整诊断示例。

最后，SKILL.md 可能膨胀成数千行。模型每次只想分析 I/O 问题，却同时加载调度器、内存回收和所有历史示例。

这会带来几个问题。

2.1 上下文浪费

并非每次任务都需要全部知识，但所有内容都占据上下文窗口。

2.2 主流程被淹没

Agent 很难从大量背景材料中快速识别真正必须执行的步骤。

2.3 指令与资料混杂

“必须执行的动作”和“供判断时参考的知识”混在一起，模型可能把示例当成规则，或者忽略真正的硬约束。

2.4 维护困难

修改某一领域规范时，需要编辑核心工作流文件，更容易引入冲突和回归。

2.5 无法有效按需加载

Progressive Disclosure 的价值没有发挥出来：虽然 Skill 只在相关时加载，但 Skill 内部仍然是“一次加载全部”。

因此，需要把稳定的工作流骨架与条件性知识拆开。

推荐把 Skill 看成下面的结构：

  • SKILL.md 是执行入口和导航层；

  • Agent 根据 SKILL.md 中的加载条件选择必要资料；

OpenAI 官方文档建议保持 SKILL.md 简洁，将 policy、Schema、示例和背景材料放入 references/，并在 SKILL.md 中说明何时读取这些文件。Anthropic 官方文档也把 supporting files 视为 Progressive Disclosure 的第三级，只在需要时读取。

4. references/ 适合放什么

大纲列出的五类内容是本章的核心：

下面分别解释。

4.1 Domain Knowledge：领域知识

例如：

  • Linux 调度延迟的判断方法；
  • 财务报表中的指标定义；
  • 法律审查中的条款分类；
  • 公司内部的业务术语；
  • 某类故障的诊断特征。

这些知识影响 Agent 如何理解材料，但通常不是每次都需要完整加载。

4.2 Spec：规范与政策

例如：

  • 组织内部审核规则；
  • 输出合规要求；
  • 协议字段定义；
  • 文档格式规范；
  • 安全审查基线。

如果规范只在某种任务中适用，就应通过条件路由加载，而不是默认塞入主流程。

4.3 Schema：数据结构说明

例如：

  • 输入 JSON Schema；
  • 报告字段定义；
  • Tool 返回结构；
  • 数据库表字段含义；
  • 事件格式说明。

需要注意：如果 Schema 是程序要直接使用的机器资源，后续也可能更适合放进 assets/。如果它主要用于让 Agent 阅读和理解字段语义，可以放在 references/。判断标准不是扩展名，而是它在工作流中的角色。

4.4 Examples：示例

适合拆出的示例包括：

  • 完整输入输出样例；
  • 边界案例；
  • 正例与反例；
  • 某种特殊场景的处理过程；
  • 不同报告类型的对照。

主文件中可以保留一个最小示例，把大量案例移到：

不过要警惕示例被模型误当成固定事实。应明确写出示例的用途和不可复制部分。

4.5 Design Docs：设计说明

例如：

  • 为什么选择某种分析路径；
  • 系统组件关系；
  • 历史兼容性决策；
  • 已知限制；
  • 术语和抽象模型。

设计说明适合帮助 Agent理解复杂背景，但不应让它替代可执行 Workflow。

4.6 API Docs：API 说明

如果 Skill 使用一个稳定、内部或离线的 API，可以提供：

  • 必要端点；
  • 参数含义；
  • 返回结构；
  • 错误语义；
  • 调用约束。

但不要无选择地复制整套 API 文档。只保留 Skill 实际使用的部分，并关注时效性。对于经常变化的外部 API，静态 reference 可能过期，应在工作流中要求查询当前官方文档或绑定受控工具。

5. 什么内容必须留在 SKILL.md

不是所有长内容都应该拆走。以下内容即使很重要，也应该留在主文件中。

5.1 Skill 的职责与边界

Agent 必须一加载 Skill 就能知道：

  • 这个 Skill 解决什么问题；
  • 不解决什么问题；
  • 输入和输出是什么；
  • 哪些情况应询问或停止。

5.4 Reference 路由规则

SKILL.md 必须告诉 Agent：

  • 哪些文件存在；
  • 每个文件解决什么问题；
  • 什么条件下读取；
  • 是否需要完整读取；
  • 多个文件同时相关时按什么顺序读取。

5.5 成功标准

输出 Contract、关键 Postcondition 和 Final Check 应保留在主工作流中。详细字段表可以拆出，但“必须通过验证才能交付”不能藏起来。

6. 拆分判断：五问法

遇到一段内容时，可以连续问五个问题。

问题一：每次执行都需要吗？

  • 是：倾向留在 SKILL.md；
  • 否：倾向移入 references/。

问题二：它是动作还是知识？

  • 告诉 Agent 必须做什么：留在主流程；
  • 帮助 Agent 理解如何判断：可以放 reference。

问题三：不读取它是否还能选择正确分支？

如果不能，分支选择规则必须留在 SKILL.md；分支内部的详细知识才可以拆出。

问题四：它是否有独立变化周期？

如果某份政策、Schema 或领域规范会独立更新，拆成单独文件更容易维护和评审。

问题五：它是否需要整体加载？

如果只会按主题查阅，应该继续按主题拆分，并提供清晰目录或标题。

可以得到一个实用决策表：

内容 每次需要 类型 推荐位置
核心执行步骤 是 指令 SKILL.md
必须遵守的安全约束 是 指令 SKILL.md
调度器事件解释 否 领域知识 references/
完整输出字段说明 条件性 Schema 说明 references/
可复制的报告模板 否 模板资源 assets/
确定性数据计算 否 可执行逻辑 scripts/
当前系统中的实时状态 动态 外部数据 Tool / MCP / API

7. references、assets、scripts、Tools 的边界

这一章虽然聚焦 references，但必须知道它不负责什么。

7.1 Reference 不是 Asset

一份报告格式说明供 Agent 理解，可以是 reference；一份要被原样复制并填写的报告模板，更适合 asset。

7.2 Reference 不是 Script

把复杂计算公式写进 reference 只能指导模型推理。如果计算要求可重复、可验证，应该由脚本完成；reference 可以解释计算含义。

7.3 Reference 不是 Tool

reference 是随 Skill 分发的静态资料，不适合表示账户余额、当前工单、最新天气等实时数据。动态事实应通过 Tool、MCP 或 API 获取。

7.4 Reference 不是另一个隐形 SKILL.md

如果一个文件拥有独立触发条件、完整工作流和独立成功标准，它可能应该成为另一个 Skill，而不是藏在主 Skill 的 reference 中。

8. Reference Routing：最重要但最容易漏掉的机制

仅仅把文件放进 references/ 不代表 Agent 会正确使用它。主文件必须包含明确路由。

8.1 差的写法

问题是：

  • 看哪个文件？
  • 什么时候看？
  • 是否全部看？
  • 看完要用于哪一步？

8.2 更好的写法

这段文字同时定义了：

  • 触发信号；
  • 文件路径；
  • 加载时机；
  • 使用目的；
  • 不应执行的行为。

10. Reference 的内部结构

一份高质量 reference 可以采用以下模板：

10.1 Purpose 防止误用

例如 scheduler-analysis.md 应明确它不能单独证明所有延迟根因，仍需与 CPU、I/O 和应用时间线交叉验证。

Skill reference 的价值不在于覆盖所有背景，而在于支持工作流中的判断。

10.4 Known limitations 防止过度泛化

例如规则只适用于某些内核版本、数据源或采样方式，就应该明确说明。

13. 时效性、来源与安全

13.1 静态知识会过期

政策、API、产品行为和版本兼容表都可能变化。reference 应记录：

  • 来源；
  • 适用版本；
  • 最近核验日期；
  • 哪些事实必须在执行时重新验证。

不要仅因为资料随 Skill 分发，就把它视为永远正确。

13.2 外部资料不是自动可信

从网页、仓库或第三方 Skill 复制进来的 reference 可能包含：

  • 恶意指令；
  • 数据外传要求；
  • 与主 Skill 冲突的规则；
  • 已过期内容；
  • 伪装成资料的 Prompt Injection。

Anthropic 官方安全说明建议像审查软件一样审查 Skill 的所有文件，而不是只看 SKILL.md。

13.3 Reference 不应偷偷升级权限

reference 是知识材料，不应通过隐藏指令要求 Agent：

  • 访问无关文件；
  • 调用额外网络服务；
  • 覆盖用户数据；
  • 绕过确认；
  • 忽略系统或用户指令。

13.4 冲突时谁优先

一般应遵循：

reference 不应成为改变上层指令优先级的通道。

15. 工程意义

合理使用 references/ 会带来五方面收益。

15.1 上下文更经济

只加载当前任务真正需要的知识。

15.2 工作流更清晰

核心指令从背景材料中被重新凸显出来。

15.3 模块可以独立维护

领域专家可以分别维护调度、内存、I/O 或政策资料。

15.4 评审边界更清楚

工作流改动和知识更新可以采用不同评审策略。

15.5 更容易演进为多 Skill 系统

当某个 reference 逐渐形成自己的触发条件、工作流和产物时，可以识别出它已经适合升级为独立 Skill。

16. 常见错误

16.1 把所有内容都移出 SKILL.md

主文件只剩“请阅读 references”，Agent 无法立即理解工作流。

16.2 只拆文件，不写加载条件

这会让 Agent 要么忽略文件，要么全部读取。

16.3 建立一个巨大的 all-in-one reference

只是移动了问题，没有实现按需加载。

16.4 文件名没有语义

misc.md、notes-final-v2.md 无法支持可靠路由。

16.5 嵌套引用过深

Agent 可能只读取入口文件，漏掉深层关键规则。

16.6 把强制规则藏进条件 reference

如果文件没有加载，强制规则就不会进入上下文。

16.7 把实时信息保存为静态 reference

最终会产生过期事实，应改由 Tool 或当前官方来源提供。

16.8 把可执行逻辑写成自然语言资料

需要稳定计算或校验时，应交给 scripts/；第 13 章会详细讨论。

16.9 示例过多且缺少标注

模型可能复制案例中的姓名、数字和结论。示例应明确区分固定格式与虚构数据。

16.10 Reference 与 SKILL.md 规则冲突

知识文件不应重新定义主流程。发现冲突时要统一来源，而不是依赖模型自行选择。

17. 博客总结

references/ 并不是“放不下的文字仓库”，而是 Skill 的按需知识层。

好的拆分应满足：

OpenAI 官方文档明确把政策、Schema、示例和背景材料列为适合放入 references/ 的内容，并要求从 SKILL.md 引用这些文件、说明何时加载。Anthropic 官方文档则进一步强调 Progressive Disclosure、避免深层嵌套，并建议在主文件变长时将详细内容拆分出去。

判断一段内容是否应该放进 reference，最关键的问题不是“它长不长”，而是：

它是每次都必须执行的主流程，还是只在某个条件成立时才需要读取的知识？

18. 学完检查题

  1. SKILL.md 与 references/ 的核心职责分别是什么？
  2. 为什么“把所有内容移到一个 all-knowledge.md”不算真正的 Progressive Disclosure？
  3. 哪些强制规则不能拆进条件性 reference？
  4. Reference Routing 至少需要说明哪四项信息？
  5. Schema 在什么情况下适合放 reference，什么情况下更像 asset？
  6. 为什么动态 API 状态不适合保存为静态 reference？
  7. 深层嵌套引用可能造成哪些问题？
  8. 怎样测试 Agent 是否只加载了相关 reference？
  9. 一个 reference 何时应该升级为独立 Skill？
  10. 为什么 reference 也需要安全审查和时效性管理？

19. Skill 专项复盘

19.1 这个逻辑应该写在 SKILL.md 还是 reference？

核心步骤、强制约束、路由条件写入 SKILL.md；条件性领域知识、详细规范和大量案例写入 reference。

19.2 这个步骤应该交给 LLM 还是 script？

读取资料、理解语义和做有上下文的判断可以交给 LLM；确定性计算和校验应优先交给 script。下一章会专门展开。

19.3 这个能力应该是 Skill 还是 Tool？

reference 本身既不是 Skill，也不是 Tool。它没有独立触发和完整工作流，也不执行外部动作，只向当前 Skill 提供知识。

19.4 什么条件下应该触发这个 Skill？

由 name 和 description 决定 Skill 是否触发；reference 不应单独参与全局 Skill Discovery，而应在 Skill 内部由路由条件选择。

19.5 如何证明拆分比不拆分更好？

通过对照实验测量 reference 选择准确率、无关加载率、工作流遵从、输出质量、上下文成本和延迟，而不是只看目录是否整洁。

20. 本章实践

选择一个现有的长 SKILL.md，执行以下练习：

  1. 标记每一段是 Workflow、Constraint、Domain Knowledge、Example、Schema 还是 Template；
  2. 保留所有核心步骤和强制规则；
  3. 将条件性知识按任务主题拆成 3～5 个 reference；
  4. 为每个文件写清 Purpose、Read this when 和 Known limitations；
  5. 在 SKILL.md 中加入明确的 Reference Routing；
